# Kernel: boot chain, stock-kernel facts and the mainline port

Read this before working in `kernel/` or on anything that boots a kernel
other than the stock one. Observed on the R1 with patched firmware 1.6 on
2026-10-22 unless marked otherwise.

## Boot chain (verified)

- **Bootloader:** `mtd0` holds only a U-Boot SPL (`U-Boot SPL 2013.07-g3fccbcd`, built 2025-01-16). It uses about 16 KB of the 512 KB partition, the rest is erased. It boots Linux directly (falcon mode); there is no full U-Boot, no U-Boot console and no display init, so nothing lights the screen before Linux.
- **Kernel slot:** the first bytes of `/dev/mtd5` (`ota`) read `ota:kernel`, space-padded. The SPL also knows `ota:kernel2`, which boots `kernel2` + `rootfs2`.
- **Slot choice and the recovery (read from the SPL dump and the recovery rootfs, 2026-10-23):** the SPL boots `kernel2` + `rootfs2` when `ota` reads `ota:kernel2` *or* when ADC channel 0 reads 1600–1800 mV at power-on, which is Volume Up held (1.65 V). The second slot is not a copy of the first: it is HiBy's recovery system (kernel built 2024-11, against 2026-01 for `kernel`; `rootfs2` is 24 MB, `rootfs` 45 MB). Its `recoveryd` mounts the SD card, loop-mounts `r1.upt` or `update.upt`, sets `ota:kernel2`, writes the update's `xImage` and `rootfs.squashfs` into `kernel` and `rootfs` (`/etc/ota_bin/local_ota_update.sh`: it writes the slot `ota` doesn't name, so never itself), then sets `ota:kernel` (`/usr/bin/bootmode.sh Normal`) and reboots. Settings → Firmware update goes through it. So stock can be restored from the card without the first slot being bootable, as long as `uboot`, `kernel2`, `rootfs2` and `ota` stay as they are. Verified 2026-10-24: with the auto-jump `r1.upt` at the card root, Volume Up held while switching on showed HiBy's upgrade progress screen, and the R1 then started normally into mainline, about 25 s after the progress screen appeared. The recovery leaves `r1.upt` on the card. It wipes `/usr/data` only when `/usr/data/recovery_all` exists (`S39_recovery.recovery` in `rootfs2`); it didn't here. To look inside: `mount -t squashfs -o ro /dev/mtdblock_bbt_ro4 /tmp/r2` from stock.
- **How the SPL loads the kernel:** U-Boot's `spl_parse_image_header`: a legacy uImage is loaded by its header's load address, entry and size; there is no checksum check and no size limit beyond the 5 MB partition. Without the uImage magic it loads 768 KB to 0x80100000. The SPL itself runs from 0x80001000 (file offset 0 of `mtd0`); disassemble it at that address.
- **Command line:** baked into the SPL, one variant per slot, differing only in `root=/dev/mtdblock_bbt_ro2` vs `ro4`. Running: `console=ttyS2,3000000n8 quiet mem=64M@0x0 init=/linuxrc flashtype=nand root=/dev/mtdblock_bbt_ro2 rootfstype=squashfs ro`.
- **Kernel image:** legacy uImage (`file firmware/stock/xImage`), load and entry `0x80F00000`, a self-decompressing gzip payload of 3.7 MB. The kernel partitions (`mtd1`, `mtd3`) are 5 MB each.
- **Serial console:** UART2 at 3,000,000 baud. Where its pads are on the board is not known.
- **USB boot mode (seen 2026-10-23):** the R1 reset while Next (PC28) was held came up as `Ingenic USB BOOT DEVICE` on the Mac (USB 0xa108:0xeaef), the X1600 boot ROM waiting for a host instead of loading the SPL: Next's pin is evidently a boot-select pin. Holding Power until it switched off, then switching on without Next, booted stock normally. So never ask for Next to be held while the R1 starts. It is also a route that doesn't depend on the flash. `kernel/tools/usbboot/` boots a kernel through it into RAM, writing nothing to flash (`usbboot.py`'s docstring has the commands; done twice on 2026-10-23). What it relies on:
  - **Protocol** (Rockbox `utils/jztool/src/usb.c` and `x1600.c`): vendor requests 0 GET_CPU_INFO (bmRequestType 0xC0, answers "X1600"), 1 SET_DATA_ADDRESS, 2 SET_DATA_LENGTH, 3 FLUSH_CACHES, 4 PROGRAM_START1, 5 PROGRAM_START2 (0x40; the 32-bit argument split over wValue high and wIndex low), data over bulk EP 1. `jztool` builds on the Mac against Homebrew's libusb (override its `/usr/local` paths) and knows the R1 as `hibyr1`.
  - **DDR set-up:** the R1's RAM (ESMT M54D5121632A) is LPDDR2, not DDR2 (type 2 in the SPL dump at 0x4060). Rockbox's `usbstage1` for the R1 (`hibyr1native`, in the unmerged Gerrit chain 7833…7734, DDR in change 7836) carries the stock SPL's DDR parameters word for word; it runs at 0x8000a000, writes a result block (magic 0xc0def00d, rc) at 0x8000f000 and returns to the boot ROM. It builds with Debian's `mipsel-linux-gnu-gcc` 12 in the `r1-mainline` image given `-mno-abicalls -fno-pic -no-pie -Wl,--build-id=none`, an empty `gnu/stubs-o32_soft.h` and `elf32-tradlittlemips` in place of `elf32-littlemips` in its linker scripts.
  - **Clocks:** `usbstage1` sets only MPLL and the DDR clock; stock runs CPCCR 0x9A094410, APLL 0x02E049CD, MPLL 0x0AF0C9CD, EPLL 0x019051CD (read with `devmem` on stock). EPLL feeds the backlight PWM and I2S, so a kernel started straight after `usbstage1` needs APLL, EPLL and the bus dividers set first.
  - **Entering it without Next** (from Ingenic U-Boot 2013.07, [k1-debian/u-boot](https://github.com/k1-debian/u-boot) `arch/mips/cpu/xburst/usb_boot.c`): `devmem 0x100000cc 32 0x42575302; sync; reboot -f` from mainline (its reboot is a watchdog reset) brings the boot ROM up on USB within a second (verified 2026-10-23). The value survives until a reset reads it; `stage2` clears it, so the next reset boots from flash. A background `(sleep 1; reboot -f) &` in `adb shell` dies with the shell and never reboots.
  - **Entering it with Next:** seen once, when the R1 reset (a reboot) with Next held. Holding Next while switching on from power-off didn't enter it, twice on 2026-10-24 (timing unknown). So when mainline has no working USB or shell, the dependable way back is Volume Up recovery, not USB boot mode.
  - **Measured:** `usbstage1` reports rc 0 (DDR set up), the 11.5 MB kernel goes over in 5.6 s and reads back identical, and the kernel boots: its serial shell comes up.
  - **What a cold boot needed (2026-10-24, from `dmesg`, `clk_summary` and register dumps of a cold boot compared with a boot through `r1jump`):** four things the stock kernel had set and mainline had relied on. (1) PC25 switches the SD card slot's power and has a pull-down: without it driven high the card fails every try (`mmc0: Card stuck being busy!`, error -145), so nothing on the card starts. (2) The PWM, LCD and MSC1 clock muxes reset to SCLK_A (1104 MHz); stock sets PWM to EPLL and LCD and MSC1 to MPLL. From SCLK_A the backlight flickers visibly. They are set on the `&cgu` node (`assigned-clocks`): the CGU can't switch these muxes while a clock is on (`clk: failed to reparent lcd to mpll: -16`), and `simple-framebuffer` holds the LCD's from early on. (3) The panel's reset (PA31) is an input after a reset, so a driver that takes it `GPIOD_ASIS` never resets the panel: black screen, backlight on. (4) PC26 must be on function 0, the RTC's 32 kHz output (`rtc32k` in the stock device tree), or the Bluetooth chip times out (`command 0xfc18 tx timeout`). With these, a cold boot from USB runs r1player on screen with the card, ADB and Bluetooth up (verified 2026-10-24). The fixes are the board device tree, the `rtc32k` pin group in `pinctrl-ingenic` and the panel driver's reset request.
- **Reading the bootloader:** `cat /dev/mtd0` works over ADB (read-only use only). A dump is in `firmware/device/`.

## The stock 4.4 kernel (verified)

- **No kexec:** `sys_kexec_load` appears in `/proc/kallsyms` only as a weak stub.
- **`/dev/mem`:** reads all 64 MB of RAM, kernel included. `kptr_restrict` is 0.
- **Memory map:** kernel text and data run from `0x80010000` (`_text`) to `0x808f9b10` (`_end`); the init section from `0x807a2000` is freed after boot. Physical address = virtual − `0x80000000`.
- **Reading stock code:** there's no vmlinux, but a function can be disassembled from RAM: find it in `/proc/kallsyms`, `dd` its pages out of `/dev/mem` on the device, `adb pull`, and run `mipsel-linux-gnu-objdump -D -b binary -m mips:isa32r2 -EL --adjust-vma=<page addr>` in the `r1-stock-modules` image.
- **Watchdog and reboot:** the stock `ingenic_wdt` driver's restart handler arms the watchdog for 160 ticks, so `reboot` is itself a watchdog reset. The X1600 watchdog doesn't use the JZ4740 register layout; `r1jump`'s `arm_watchdog` copies the stock sequence, and `insmod r1jump.ko wdt_only=1 wdt_secs=5` reset the R1 as expected.
- **Module loading:** accepts unsigned out-of-tree modules with no symbol versions. Vermagic is `4.4.94+ preempt mod_unload MIPS32_R2 32BIT `.
- **Building modules:** `kernel/tools/stock-modules/build.sh` builds them from a vanilla kernel.org 4.4.94 tree whose `struct module` matches stock. Check a result with `layout.py` and `imports.py`, run as `uv run --with pyelftools python ...` (the latter needs `/proc/kallsyms` saved to `kernel/out/stock-kallsyms.txt`). The `probe` module loads and unloads on the device.
- **Trap: inline helpers.** Only `struct module` is known to match. Inline helpers that read other kernel structs compile cleanly but misbehave: `alloc_page()` returned NULL on the first call with plenty of free memory. Other examples are `page_to_phys`, `page_address`, `file_inode`, `i_size_read` and `kmalloc`/`kcalloc` (which index the slab caches inline). A module must stick to exported functions (for example `__get_free_pages` and `kernel_read`), and `imports.py` must report nothing missing. `r1jump` follows this and its dry run works.
- **Trap: the OOM killer reboots the R1.** About 15 MB is available while `hiby_player` runs. When a module or `/tmp` (tmpfs, so RAM) takes more, the OOM killer picks `hiby_player` and its launcher reboots the device; this happened with an 8 MB image in `/tmp` plus `r1jump`'s 8 MB copy. Allocate in modules with `__GFP_NORETRY | __GFP_NOWARN`, which in 4.4 fails instead of invoking the OOM killer (verified on the same case).
- **busybox `insmod`** calls a module's init twice when it fails, so its log lines appear twice, and reports a missing file (r1jump's `image=`, after a reset wiped `/tmp`) as "unknown symbol in module, or unknown parameter".

## Mainline status (checked against torvalds master, 7.3 / 7.4 merge window, 2026-10-22)

- **No X1600 platform:** there's no `MACH_X1600`, no X1600 clock (CGU) driver and no `x1600.dtsi`. Ingenic support stops at the X1000 and X1830.
- **Already X1600-aware:** `pinctrl-ingenic` (full X1600 pin data, `ingenic,x1600-pinctrl` and `ingenic,x1600-gpio`, compiled in only with `CONFIG_MACH_X1600`, which upstream doesn't define; our patch 0001 adds it), dwc2 (`ingenic,x1600-otg`). Verified in the 7.3 release; master's `pinctrl-ingenic.c` was identical on 2026-10-22. (A note in between wrongly said 7.3 lacked the pin data: a `grep -rl ... | head` cut the list before reaching it.)
- **Reusable as is (verified 2026-10-23):** OST and MMC through the X1000 compatibles, PDMA through the X1830's (plus a NULL-dereference fix, patch 0014). **Not as is:** I2C and I2S each differ from the X1000 in one register and got `ingenic,x1600-*` entries (patches 0010, 0011). The UART runs through `ingenic,x1000-uart` once UMR is reset (Bluetooth, below) and the TCU through `ingenic,x1000-tcu` (watchdog, below); the X1600's PWM is its own controller (display, below). Untried: SPI (SSI).
- **Board chips covered:** CS43131 (`cs43130` driver), CW2015, BCM43430 Wi-Fi (`brcmfmac`), the touch panel (`hynitron,cst816s`, verified 2026-10-23).
- **Missing:**
  - the Ingenic SFC (the internal NAND flash controller): patches 0051–0053 add it (below);
  - the X1600 LCD and PWM controllers and the LG35583 panel (our patches 0024–0032 add them; the X1600's LCD controller has nothing in common with `ingenic-drm`'s);
  - Rust-for-Linux (no MIPS support).

## Internal flash (SFC; reads 2026-10-24, writes 2026-10-25)

- **Chip:** Winbond W25N01GV, mainline's SPI-NAND core identifies it ("Winbond SPI NAND was found": 128 MiB, 128 KiB blocks, 2048-byte pages, 64 OOB bytes, on-die ECC). No bad blocks on this unit.
- **Driver (patches 0051–0053):** `spi-ingenic-sfc.c`, a spi-mem controller with programmed I/O only (no interrupts, no DMA), on the register map and sequence of Rockbox's X1600 port (`sfc-x1600.c`): stop, direction in GLB, the transfer mode in TRAN_CFG1 (0x9c, not TRAN_CONF as on the X1000), command, length and address, flush, start, then the FIFO in bursts of the 32-word threshold on TREQ/RREQ, then END. The SPI clock is a quarter of the SFC clock: at 24 MHz the SFC read 660 KB/s; at `spi-max-frequency` 37.5 MHz (SFC 140 MHz, MPLL / 10) with quad reads and Rockbox's W25N timing (TSH 11, sample delay 1) 4.2 MB/s for 5 MB and 8.3 MB/s for the whole 128 MiB. Zhou Yanjie's 2022 interrupt/DMA driver (never merged; catplay-labs keep a copy for the X1600) was the other reference.
- **No pinctrl:** the boot loader sets PC17–PC22 up. pinctrl-ingenic's X1600 "sfc" group also takes PB4 (function 2), which is the R1's Bluetooth power.
- **Partitions:** stock keeps its table in the flash (`mtd0` at 0x5800, magic "nand"); the device tree copies it, all `read-only`, plus `hiby` (0x7d00000, 3 MiB), the MAC, serial and licence data the vendor kernel hides from its MTD device. No bad-block table on the flash: stock and mainline both read the block's first OOB byte(s), and the BBT stays in RAM.
- **Verified (reads):** `mtd0` equals `firmware/device/uboot-mtd0.bin`, `mtd1` starts with the installed flash image, `mtd2` with the auto-jump `rootfs.squashfs` (37.5 MB), all md5-equal; no ECC failures or corrected bits over the whole flash; `userdata` starts with "UBI#", `rootfs2` with "hsqs". UBI isn't built in, so nothing attaches to `userdata`.
- **Writes (2026-10-25):** the device tree drops `read-only` from `kernel` and `rootfs` only (patch "let the kernel and rootfs partitions be written"); `/sys/class/mtd/mtdN/flags` reads 0x400 (`MTD_WRITEABLE`) for mtd1 and mtd2 and 0 for the six others, so the MTD layer refuses to erase or write the boot loader, HiBy's recovery, `ota`, `userdata` and `hiby`. Busybox has no flash tools, so `kernel/tools/r1flash.c` (static, built by `build.sh` into `out/r1flash`, pushed to `/tmp` when needed, not in the image): `write` (block by block, each read back), `test` (a pattern on erased blocks, read back, erased again) and `dump`; it refuses a range with a bad block. Verified: `r1flash test /dev/mtd2 0x2c80000 4` on the last 4 blocks of `rootfs` (the stock squashfs ends at 0x23c57f2, its `bytes_used`) read the pattern back and erased them again, and two flash kernel installs read back md5-equal.
- **Not done:** DMA, quad writes, UBI on `userdata`.

## Replacing stock in flash (installed 2026-10-24)

The user's goal is to drop stock. The design: a mainline kernel in the `kernel` slot (mtd1), with `uboot`, `kernel2`, `rootfs2` and `ota` left untouched, so Volume Up at power-on with a stock or auto-jump `r1.upt` on the card restores the current system through HiBy's recovery (verified, "Boot chain" above). Not `kernel2`: that slot is the recovery.

- **Image:** `build.sh` writes `out/r1-linux.uimage`: the xz-compressed self-decompressing kernel (`vmlinuz.bin`) with the DTB appended, in a legacy uImage header (`tools/mkuimage.py`; the build image has no `mkimage`). It must fit 5 MiB, because the flash kernel carries everything it needs before the card mounts (it has no flash driver; the card kernel reads the flash since patches 0051–0053); `build.sh` fails over 5,242,880 bytes (5,049,639 on 2026-10-24, 5,125,838 on 2026-10-25; with `CONFIG_MODULES`, every exported symbol's table entry made it 5,294,194 bytes, 133 KB more, until `TRIM_UNUSED_KSYMS`). Since 2026-10-25 the flash kernel is the minimal one (`r1.config`) and the card kernel, which has no such limit, carries Wi-Fi (`r1-card.config`): 12.4 MB uncompressed. The decompressor runs at `CONFIG_ZBOOT_LOAD_ADDRESS` 0x81000000: the default (the kernel's end rounded up to 64K) left 2.5 KB between the unpacked kernel and the decompressor, and the decompressor copies the DTB into that gap while it still runs; `build.sh` checks the copy stays below it. `CONFIG_KEXEC` brings `CRASH_DUMP` by default, which links the kernel at 0x84000000: it is off.
- **What the SPL passes:** a0 = 2, a1 = an argv array at 0x80000800 (argv[0] NULL, argv[1] its command line), a2 = 0 (`jalr` at 0x80002eec in the SPL dump). a0 isn't -2, so the kernel uses its appended DTB, and `MIPS_CMDLINE_FROM_DTB` makes it ignore the SPL's `init=/linuxrc root=…`. `usbboot.py --uimage --spl-args` boots the image from RAM the same way; verified 2026-10-24.
- **Updates without stock (`initramfs/r1-loader`):** the flash kernel kexecs the card's `/.r1-mainline/r1-linux.bin`, so a new kernel only needs copying to the card. One image plays both roles: a kernel the SPL started finds the cause of the reset in RSR (0x10000008), which `r1-loader` clears, so a kernel started by kexec (or by `r1jump`, after `r1-mainline.sh` cleared it) finds 0. Before the kexec it sets CPSPR (0x10000034, a CPM scratch register; its write lock CPSPPR 0x10000038 opens with 0x5a5a and closes with 0xa5a5) to "R1KX"; the card kernel's init clears it once up. A watchdog reset keeps CPSPR (seen: a value set before a reset read back after it), the stock SPL never touches it, and Rockbox's `usbstage1` clears it (so `stage2` puts back the value `usbstage1` reports). Found still set after a reset, the card kernel failed: the flash kernel carries on itself, once. That doesn't survive holding power to restart (seen 2026-10-24: a card kernel that hung started again at every restart), so since 2026-10-25 the flash kernel also writes `/.r1-mainline/kexec-pending` (the card kernel's size and mtime) before the kexec, and the card kernel's `r1-loader done` removes it (only there: `/tmp/r1-loader.kexec` marks a kernel started by kexec). Found naming the same kernel, the flash kernel stays on itself until a different `r1-linux.bin` is copied (or the file is removed). Verified with a two-instruction loop as the card kernel: the watchdog reset it, the flash kernel stayed ("didn't come up last time"), stayed again on the next restart with CPSPR clear ("the card's kernel (8 1792916765) didn't come up last time: staying on this one until it changes"), and handed over again once the real kernel was back. Volume Down held while the R1 starts (verified 2026-10-24: "Volume Down held: staying on this kernel") or `.no-kexec` at the card root also keep the flash kernel. `r1kexec` is a 2.7 KB libc-free `kexec_load` of one segment, a0-a3 = 0; static glibc made it 670 KB.
- **Measured from RAM (2026-10-24):** the flash image hands over to the card kernel (its `dmesg`: "reset cause 0: started by kexec"; ADB about 12 s after the USB load ends). The watchdog keeps running across kexec (the core stops it only for halt, power-off and `SYS_DOWN`; a kexec goes through restart): kexec into a two-instruction loop reset the R1 5 s later, and the next start stayed on the flash kernel ("the card kernel didn't come up last time"). Not tried: Volume Down. The X1600 display driver's shutdown hook turns the display off before a kexec, which the jump from stock needed `boot.sh` for.
- **kexec needs the caches written back (patch 0058, 2026-10-25):** mainline's MIPS `relocate_new_kernel` copies the new kernel through KSEG0 and jumps with only a `sync` (Octeon alone flushes), so on the X1600 the lines still in the D-cache at the jump aren't what instruction fetches see. Every card kernel built with `CONFIG_MODULES` died that way, before the console was up (no pstore log; ADB back about 23 s after the restart with the flash kernel up 4–5 s, "didn't come up last time"), while the same kernel without it, and one padded to the same size with random data, booted. A mark word in RAM (boot marks, below) put the death in the first `printk` of `start_kernel`, after `page_address_init`. The patch writes back and invalidates the D-cache and L2 and invalidates the I-cache by index before the jump, from the geometry `machine_kexec()` stores beside the relocated code. The fix runs in the kernel that does the kexec, so it needed a flash install; with it the module kernel came up. Without it, a module-free card kernel failed to come up once too (2026-10-25). It isn't what caused the "after a kexec that followed heavy writes" SD setup timeouts (SD DMA, below): side builds with it still had small reads that never finished.
- **USB lost at some starts (2026-10-25; cause not found):** some starts after a restart (`r1-reboot`, a watchdog reset) had no USB at all, for any port, cable or replug: `dwc2_core_reset: HANG! Soft Reset timeout GRSTCTL_CSFTRST`, then "probe with driver dwc2 failed with error -16", already in the flash kernel's probe straight after the boot loader, then in the card kernel's. Probing again, after SRBC's OTG_SR and a PHY POR pulse too, timed out the same way, with CPM's CLKGR, OPCR, USBPCR, USBPCR1 and SRBC as in a good start and GRSTCTL stuck at 0x80000001 (AHBIdle, CSftRst never clearing: no PHY clock). A restart often failed again; a power-off always cleared it. `poweroff -f` doesn't come back by itself on USB power, so software can't power-cycle the R1. Restarts in loops (`try.sh`), counting starts with USB:
  - this morning's flash and card kernels (`6480da5`): 22 of 22;
  - that flash kernel, with today's card kernel (no modules): 25 of 25;
  - that flash kernel plus the kexec cache fix (0058): 25 of 25;
  - that flash kernel plus the Wi-Fi nodes (0057): 1 failure in 22;
  - today's patches with this morning's config, Wi-Fi nodes disabled: 12 of 12; the same plus `CONFIG_MODULES`: two failures within a few starts;
  - today's patches and config (modules on): about 1 failure in 5; with the Wi-Fi nodes disabled in both kernels, two in 5; without modules but with Wi-Fi in the flash kernel, 1 in 12;
  - today's tree, flash kernel without Wi-Fi nodes and modules (what is installed): 25 of 25;
  - 2026-10-25 evening, side builds of the flash kernel from `51d4b35` (worktree `/src/usbdelay`, build directory `/src/build-usbdelay`) plus `CONFIG_MODULES` and `TRIM_UNUSED_KSYMS`, Wi-Fi nodes disabled, with today's card kernel (no modules) and `r1-reboot` once the uptime passed 40 s, USB idle: as is, 1 failure in 10 (the 9th start, the HANG at 0.816 s in the flash kernel and again in the card kernel; r1-usb's restart brought USB back); the same plus `msleep(2000)` at the start of `dwc2_driver_probe`, before it touches the PHY or the core (a `DEBUG` commit in the worktree only): 30 of 30, in two runs of 15 around the failing one. At the 1 in 10 seen here, 30 clean starts happen by chance about 4% of the time (0.9^30);
  - that failing build (no delay), the restart preceded by a soft-disconnect (DCTL.SftDiscon set over `devmem`, then 0.5 s for the host to see the detach, then `r1-reboot`), 2026-10-25: a failure in the third start, and r1-usb's restart failed too (a power-off brought USB back). The host seeing a link across the restart is not the cause;

- **Installed 2026-10-24:** the R1 starts mainline from flash, hands over to the card's kernel and runs r1player with USB, ADB and Bluetooth; no HiBy logo or stock phase on screen.
- **USB needed its PHY (found by the install):** the first install came up without USB, even after a replug. After a reset the X1600's USB PHY is gated (OPCR bit 23) and suspended (OPCR's SPENDN0, bit 7); the boot ROM's USB loader and the stock kernel turn both on, so every earlier test (through `r1jump` or USB boot mode) had USB. Fixed by patches 0046–0049: the CGU's `usb_phy` clock does both, and `phy-ingenic-usb` gets an `ingenic,x1600-phy` entry that writes the boot ROM's values (USBPCR 0, USBPCR1 `BVLD_REG`) and pulses POR, as Rockbox's R1 port does. dwc2's probe gates and suspends the PHY through that clock and its gadget start turns it on again, so any boot exercises the cold path. Patch 0050 fixes a `regulator_disable` warning `phy-ingenic-usb` gave at every probe (exit disabled the supply power_off had already disabled).
- **kexec from a running system:** with r1player and Bluetooth up only about 21 MB is free, and `r1kexec` (its 11.5 MB buffer plus the kernel's copy) is OOM-killed (`Killed`, exit 137). `r1-loader` runs before them, with about 49 MB free. - **What the X1600 needed:**
  - **PRId:** the core reports 0x00d00000 (company Ingenic D0, implementation 0), which `cpu_probe_ingenic()` rejects with a silent `panic("Unknown Ingenic Processor ID!")` before any console exists. The X1600 manual (2.2) gives it as "0x00D0000", a digit short. Patch 0003 (since 2026-10-25 the Letux kernel's version) handles it on the X1830's path (`PRID_IMP_XBURST_REV2`: write-combine only), not on the older `REV1` path, which also clears MIPS32r2 and writes `HPTLB_DIS`. That workaround isn't needed: booted cold through the boot ROM's USB loader (no kernel ran before it), the kernel reaches userspace without it (2026-10-25), and `/proc/cpuinfo` lists mips32r2.
  - **OST timer:** same registers as the X1000 (`ingenic,x1000-ost`), but on CPU interrupt 4, not 3. Its only clock input is a fixed 24 MHz `ext`.
  - **Interrupt controller:** the X1000/JZ4780 one at 0x10001000, on CPU interrupt 2.
  - **Display, until its driver probes:** stopped. `boot.sh` stops the controller (CTRL 0x13052000 bit 4, then waits for bit 0 of 0x13052004 to clear) with r1player paused, before the jump, so the screen stays dark from the jump until mainline's display driver starts it (about 1.5 s), and `simple-framebuffer`, the console and the boot-mark stripes draw into memory nothing shows. Left running through the jump it sometimes halted for good (below). Until 2026-10-23 it was left running: the controller rereads a self-linked frame descriptor (register 0x1000) every frame, the stock kernel allocates that descriptor anywhere and replaces it when r1player flips pages, so `boot.sh` chained it to a self-linked copy showing page 0 in the last row of page 1 (0x02776F00), memory of the stock framebuffer that the device tree still reserves. Three ways that went wrong first: assuming a fixed address (the console ended up on the hidden page); a page just past the framebuffer (r1jump allocated it as free memory and overwrote it, and the screen went to garbage); and the boot marks painting both pages (the last stripe overwrote the descriptor, giving vertical lines).
  - **The stock device tree** is readable at `/sys/firmware/fdt`; a decompiled copy is in `kernel/out/stock-dt/` (untracked) and gives every block's address and interrupt.
- **USB (stage 2, 2026-10-23):** the DWC2 at 0x13500000 (`ingenic,x1600-otg`, intc 1) works as a peripheral, with the PHY and clocks as the stock kernel left them. The built-in `g_serial` gadget gives a shell on `/dev/cu.usbmodem*`. `dr_mode = "peripheral"`: host mode needs the USB-C controller as a source and VBUS on PC24 (see "USB-C role" below).
- **SD card (stage 2):** on **MSC1** (0x13460000, intc 36), not MSC0, despite the stock tree's `mmc0` alias pointing at MSC0 (MSC0 is probably the Wi-Fi chip's SDIO link). The X1600's MSC has the X1000's JZ layout, so `jz4740_mmc` (`ingenic,x1000-mmc`) drives it; the stock kernel's many `sdhci_*` symbols are a red herring. It ran in PIO until 2026-10-24, and now uses the MSC's integrated DMA (patch 0054), and the initramfs mounts the exFAT partition read-only at `/mnt/sd_0`.
  - **DMA (patch 0054, 2026-10-24):** the X1600 has no PDMA request lines for its MSCs (the stock device tree gives them no `dmas`; Ingenic's kernel uses the MSC's own descriptor DMA, as Rockbox does on the X1000), so `jz4740_mmc` now drives that integrated controller from the X1000 on when the tree names no channels. Descriptor: next, address, length, command (LINK bit 0, ENDI bit 1); DMANDA 0x48, DMADA 0x4c, DMALEN 0x50; DMAC 1 (enable, DMA_SEL clear). Trap: no flag reliably marks the end of a read on the X1600. DMA_DATA_DONE (IFLAG bit 31, which Rockbox waits for) never came, and DMAEND (bit 16) came for the 8-byte SCR read but not for the 64-byte SD status read right after, whose DMADA had advanced by 0x40 and DMALEN reached 0; waiting on either flag left the card uninitialised (a first boot on it went black and needed Volume Down). A read now counts as done when DMADA reaches the end of the last segment with DMALEN 0, or on DMAEND. Second trap (2026-10-25): after a kexec that followed heavy writes, the 8-byte SCR read (CMD51) at card setup sometimes never raised DATA_TRAN_DONE although DMADA had reached its end, so each try timed out after 5 s and the setup started over (up to 24 s, four tries, past init's former 10 s wait). Caught with a register dump in the request timeout: `cmd 51 data read ... ireg 00002000 ... da 01e25f08 len 00000000 end 01e25f08`. Transfers under 512 bytes (only the card's registers at setup) now go through PIO. Not tested: other SoCs (the integrated DMA is used from `JZ_MMC_X1000` up when the tree names no `dmas`; upstream X1000/X1830 trees all name them), error paths (CRC errors, a card pulled mid-transfer), suspend and resume, SDIO; the 64 KiB descriptor length limit is a choice, not checked against DMALEN's width. Upstream would likely want an `ingenic,x1600-mmc` compatible that turns it on explicitly. Measured with `dd` on the R1 (a 28 MB file cold, 32 MB written with `fsync`): PIO 17.3 MB/s read, 13.9 write; integrated DMA 22.3–22.5 read, 14.5–18.2 write (the lower figure with r1player indexing at the same time), the CPU free during transfers. Checked: three files' md5 against the Mac's, and 8 MB of random data written and read back after dropping caches. How it was debugged without risking boots: a module parameter turned it on per probe, and the driver was unbound and bound again live with the card unmounted (nothing runs from the card since the system moved to flash). MSC_STAT doesn't mark it either (2026-10-25, a side build of `r1` 7c181b8): with MSC_STAT bit 16 (DMAEND, which the manual documents without the mask condition it gives the IFLG bits) as the read-done test, CMDAT RTRG/TTRG at 32 (as Rockbox sets them) and no 512-byte cutoff, 52 of the first 78 reads timed out, the 64-byte SD status read every time, with `status 1f000040` (bit 16 clear), `iflg 00002000`, DMADA at the end and DMALEN 0; the card wasn't initialised (`error -5 whilst initialising SD card`), and the next start stayed on the flash kernel as designed. IMASK still masked DMAEND and DMA_DATA_DONE in that run, so whether the IFLG bits come when unmasked (the X1600 manual: IFLG.DMAEND is set only while IMASK.DMAEND is 0; Rockbox unmasks DMA_DATA_DONE and waits for its interrupt) is still untested. Unmasked (2026-10-25, side builds of `r1` 2813bb1, so with the kexec cache fix 0058): with DMA_DATA_DONE, WR_ALL_DONE and DMAEND unmasked from the DMA start and recorded by the hard IRQ, and no 512-byte cutoff, **DMAEND came** for the 8-byte SCR and the 64-byte SD status reads (`seen 00010000`, IMASK `7f7fffff`), while **DMA_DATA_DONE never came even unmasked** (`iflg 00002000`); a later small read then never finished (`error -145 whilst initialising SD card` at 7 s, so 0058 did not cure the small-read hang, though unmasking all three may play a part), and the start fell back to flash. With only DMAEND unmasked, the cutoff kept and the address check as fallback, the card came up cleanly (mounted at 7.8 s, no timeouts, no reads without DMAEND logged), but every read was very slow: init's `ls /mnt/sd_0` took about 2 minutes, with 877 MSC1 interrupts in 345 s at 91% I/O wait. Not yet explained; a guess is that the DMAEND interrupt meets the threaded handler, which keeps the line masked (ONESHOT) while it polls, so reads wait out the 10 ms poll. Recovered with `.no-kexec` at the card root.
- **X1600 clock driver (`x1600-cgu.c`, stage 3a, 2026-10-23):** the register map was read out of the running stock kernel, not guessed. `kernel/tools/stock-modules/clkdump` (a stock-kernel module; only exported functions plus `__clk_lookup` through `kallsyms_lookup_name`) logs every stock clock with its rate, parent, ops symbol and the raw driver structure behind it; `kernel/tools/clkdecode.py` groups them by type. Each mux's parent list came from its `clk_core` (`parent_names` at +20, `num_parents` at +28, verified by the name at +0) read through `/dev/mem`, and the vendor tables `ingenic_mux_table` (identity), `x1600_clk_div_table` (MSC: 2(n+1)) and the PLL descriptors from their kallsyms addresses. The raw dump is `kernel/out/stock-dt/clkdump.txt` (untracked).
  - **PLLs:** rate = ext × M / (N × OD1 × OD0), M bits 31:20, N 19:14, OD1 13:11, OD0 10:8, no offsets (the vendor descriptors say so). The driver keeps them, and the CPU, L2, AHB, APB and DDR clocks, read-only.
  - **Muxes:** register value = parent index. SCLKA {stop, ext, APLL}; CPU/L2, AHB0, AHB2/APB, DDR {stop, SCLKA, MPLL}; peripherals {SCLKA, MPLL, EPLL} (CAN adds ext); I2S {SCLKA, EPLL}.
  - **CDR dividers:** as on the X1830 (change enable 29, busy 28, stop 27), 8 bits wide (4 for PWM and DDR). **Gates:** set-to-disable bits in CLKGR0 (0x20), CLKGR1 (0x28) and OPCR (0x24, bit 23 for the USB PHY). **I2S:** transmit at 0x7c and receive at 0x60, each a mux on bit 30 {SCLKA, EPLL}, an M/N fractional divider (rate = parent × M / N, M bits 28:20, N bits 19:0), an output enable on bit 29 and a gate in CLKGR1 (bit 9 transmit, bit 8 receive). Not in the driver yet: CAN, CDBUS and the memory power gates at 0xf8/0xfc.
  - **Check:** `kernel/tools/clkcompare.py` compares mainline's `clk_summary` with the stock dump: all 50 rates and gate states matched on the first boot.
- **Pins:** the X1600 pin controller (`ingenic,x1600-pinctrl`, 0x10010000, ports A–D every 0x100, GPIO interrupts 17/16/15/14 on intc) claims the SD card's pins (PD0–PD5, `mmc1`). Its GPIO registers (0x10–0x40, 0x70–0x90 per port) read identical under stock and under mainline.

- **Audio (stage 4, 2026-10-23):** a 440 Hz tone plays cleanly on the headphone output at 44.1 kHz; 44.1 and 48 kHz run at the right rate (measured from the PCM hardware pointer: 44,077 and 48,146 frames/s over 3 s). The chain is all mainline drivers: PDMA (`dma-jz4780` as an X1830, intc 3, AIC request lines 62 TX and 63 RX), the AIC (`jz4740-i2s`, intc 0) as I2S master, the I2S clock from EPLL, and the CS43131 (`cs43130`) on a bit-banged I2C bus (`i2c-gpio`, PB30/PB31, address 0x30, as the stock firmware drives it) behind a `simple-audio-card` with `mclk-fs = 512` (22.5792 / 24.576 MHz, HiBy's MCLKs). PB2 powers the DAC (a fixed regulator) and PB21 resets it. Three driver differences, each a patch:
  - **I2SDIV** holds the bit clock divider itself (not divider − 1 as on the X1000) and keeps only even values: writing 7 stores 6. With the X1000 settings 44.1 kHz played at 58.8 kHz (patch 0010).
  - **`cs43130`** takes the DAI `set_sysclk` frequency as SCLK, but `simple-audio-card` passes MCLK there, so it set up 256-bit slots and played white noise. Patch 0012 adds `set_tdm_slot`, and the R1's DT gives the codec two 32-bit slots (`dai-tdm-slot-num`/`-width`).
  - **`dma-jz4780`** dereferenced a NULL descriptor in `tx_status` after `terminate_all`, which ASoC calls when a stream closes: every close panicked (patch 0014). Master had the same code on 2026-10-22 (734bef548a96). The bug dates from the driver's first commit (d894fc6046fe, 2015) and only shows since `snd_dmaengine_pcm_sync_stop()` calls `dmaengine_tx_status()`, added by 88e98af9f4b5 (v6.11-rc1).
- **Two `cs43130` bugs behind white noise in r1player (2026-10-23), each a patch:**
  - **The clock reference count (patch 0034):** ALSA calls `hw_free()` after any failed `hw_params()`, also when the failure came before the codec's own `hw_params()`, and `cs43130_hw_free()` dropped a clock reference it never took. r1player asks for S32_LE first, which the AIC refuses, then S24_LE: `clk_req` went 0 → −1 → 0, `hw_params()` skipped the switch to the external MCLK, and the DAC ran from its RC oscillator. Every signal then hissed (digital silence stayed silent); r1tone, which opens S16_LE directly, played clean. Check it in `/sys/kernel/debug/regmap/0-0030/registers`: `010006` reads 04 (external MCLK) while a stream plays, 06 (RC oscillator) otherwise. The patch keeps the DAIs holding a reference in a bitmap.
  - **No mute while stopped (patch 0033):** the PCM path stays unmuted until DAPM powers down, `pmdown_time` after close, and a stopped stream hisses at 0 dB. The patch adds `mute_stream`, so ASoC mutes at `hw_free()` and unmutes at `prepare()`. Not on trigger: `mute_unmute_on_trigger` runs in atomic context, and the codec is on I2C. A stream that is open but stopped still hisses, so r1player closes the PCM when paused or stopped.
  - **Formats:** the AIC takes S16_LE and S24_LE (24 bits in a 32-bit container), not S32_LE.
- **96 kHz and up don't work yet:** `mclk-fs = 512` asks the DAC for a 49.152 MHz MCLK, and `cs43130` accepts only 22.5792 and 24.576 MHz. HiBy keeps those two MCLKs for every rate of each family; `simple-audio-card` can't say that.
- **Mono (2026-10-23):** a mono stream gets the same DAC layout as stereo: 64-clock frame, high time 32, channel 2 at bit 32 (CS43131 registers 0x040014 to 0x040019 and 0x050000/0x050001 read over I2C at 0x30 while a silent stream runs). That layout is right on this board: two 32-bit slots go out either way, with the same divider. (This note first credited `AICCR` bit 11, `MONO_TO_STEREO`, for the mono expansion; listening showed it does nothing on the X1600, below.) **But mono also needs the AICCR channel field (bits 26:24) written** (patch 0010, which since 2026-10-24 also leaves bit 11 clear on the X1600: AICCR reads 0x000C4002 in mono and 0x010C4002 in stereo, and silent 6 s streams take 6 s in both and at 48 kHz): left at 1 (two channels, as the stock kernel leaves it), the AIC takes a mono stream two samples per frame, so it plays an octave high and 6 s of mono ends in 3 s, which an earlier "mono is clean in both ears" check missed. Check speed with silence: `r1tone 1000 -200 6 44100 <ch>` takes 6 s in both cases once fixed (2026-10-23, `AICCR` 0x000C4802 in mono; the field being a channel count was inferred from this; the X1600 programming manual has it at bits 26:24, 0 for mono and 1 for stereo, 2 to 7 reserved, bit 27 reserved; it also lists bit 11 as reserved and read as zero, yet bit 11 reads back as 1 here and the X1000 and X1830 manuals define it as `M2S` (mono to stereo), so the X1600 manual most likely omits it; listened on 2026-10-24 (440 Hz mono, `r1tone`, earbuds): with bit 11 cleared once playback ran (AICCR 0x000C4802 -> 0x000C4002, and it stays cleared) the tone sounds the same as with it set, in both ears at the same pitch, and also with it held cleared from before the PCM opens (heard twice, at -20 and -10 dBFS): bit 11 does nothing on the X1600, and mono reaches both channels without it; both tones pop when the PCM opens and again when it closes; listened to on the earbuds the same day: mono and stereo 440 Hz have the same pitch; whether mono is equal in both ears with the fix was not answered). The ASoC core produces that layout by forcing the codec's channel count to the number of `tdm_mask` bits (`soc_pcm_codec_params_fixup()`), which is what two reviewers of the `cs43130` patch object to (below).
- **Volume:** `Master Playback Volume` is attenuation in 0.5 dB steps from −127.5 dB (255 = 0 dB); it boots at 135 (−60 dB). HiBy's driver mutes the DAC around every clock start and stop; mainline mutes it from `hw_free()` to `prepare()` (patch 0033), not around the clock start and stop. Over four mono tone starts and stops on the earbuds (2026-10-23, volume 195, tones at -30 dBFS) there was at most one faint click, once, and the listener was not sure it was real. Not settled: whether mainline pops at stream start or stop; louder levels and other headphones are untested.
- **Touch (2026-10-23):** the panel at 0x15 on I2C1 (PB19/PB20, function 0; intc 60, the stock tree's i2c1; I2C0 is intc 61) works with mainline's `hynitron,cst816s` driver, interrupt PA16 (falling), reset PA17. It reports panel pixels (480 × 800), though the driver advertises 0–240. With the spike filter left long (see below) every transfer ends in a lost arbitration (TXABRT 0x1000). **The patch's premise is wrong** (checked against the manuals 2026-10-24, after Schaller pointed it out): it says the X1600 moved the SDA set-up time from 0x94 to 0xa0, but on the X1600, X1000, X1830 and X2000 alike SDASU is at 0x94 and 0xa0 is the spike suppression limit (`FSSPKLEN` on the X1600, `I2C_FLT` on the X1000; reset value 1, longest spike filtered, in APB cycles). SDASU is used only when the controller is a slave transmitter, so writing 0x94 never mattered to a master. What the patch really does is put the driver's set-up value (64 APB cycles at 400 kHz) into the spike filter, overwriting a filter left too long by whatever ran before. Measured on 2026-10-24 by driving single reads of the touch chip by hand with `devmem` (the driver rewrites both registers at the start of every transfer, so poking them between transfers tests nothing): with SDASU anywhere from 1 to 100 and the filter from 1 to 100 every read succeeds; with the filter at 110, 116, 128, 200 or 255 every read ends in TXABRT 0x1000, the original failure. SCL's high count at 400 kHz is 0x66 (102 cycles), so a filter longer than the high phase hides the controller's own clock and it thinks it lost the bus. The failure was seen when mainline was started through `r1jump`, after the stock kernel; the filter read 116 then, not the manual's reset value of 1, so the stock kernel most likely left it there (inferred). A cold boot leaves it at 1 and works without the patch. Patch 0011 now programs the filter on the X1000 and later to the I2C 50 ns (7 cycles here), and the X1600 compatible falls back to `ingenic,x1000-i2c` (patches 0009, 0013); with it the R1 reads 7 on both controllers, and a filter set to 116 by hand is put back on the next transfer (verified 2026-10-24). Sent upstream as i2c v2 the same day. Its power rail is the PMIC's ALDO2, kept always on in the DT since the driver takes no supply.
- **Keys (2026-10-23):** power on PC31 (active low) and next on PC28 (active high) through `gpio-keys`; play/pause, volume down and volume up share ADC channel 0 (0, 1.0 and 1.65 V; 3.3 V released) through `adc-keys`, polled every 50 ms. All five verified, one press each.
- **ADC (patch 0015, a new driver, `ingenic-x1600-adc`):** the SADC at 0x10070000, intc 11, has nothing in common with the JZ47xx ADCs of `ingenic-adc`. ENABLE (0x00) bits 3..0 start a channel and bit 15 powers it down; CTRL (0x08) bits 3..0 mask the channels' interrupts; STATUS (0x0c) is write-1-to-clear; results are 12 bits, channels 0/1 in 0x10 and 2/3 in 0x14 (low and high half); CLKDIV (0x20, ADCLK in the manual, 19.5.2.7) holds an even divider from the device clock in 7:0 (an odd N divides by N−1) and, in 15:8 and 31:16, the microsecond and millisecond dividers that only repeated sampling uses. Stock writes 119, 1, 99 at the 140 MHz APB clock (119 divides by 118, and 1 is outside the manual's range for the microsecond divider); since 2026-10-25 the driver writes 120 and leaves the other two at their reset values (16, 4), which converts as before. Reference 3.3 V. Channels: 0 the keys (<< about 0.03 V, − 1.06 V, + 1.65 V, read 2026-10-25; the DT, as stock, reports << as `KEY_PLAYPAUSE`, not `KEY_PREVIOUSSONG`; >> is a GPIO key, PC28, `KEY_NEXTSONG`, and power PC31), 1 the headphone jack (stock reads 2.8–3.3 V as plugged; about 3.3 V with earbuds in), 2 the headset remote (2.0 V idle; stock powers it from the PMIC's ALDO4), 3 unused. Jack detection and the remote aren't wired up yet.
- **Display (stage 3, 2026-10-23, patches 0024–0032):** mainline's own driver now runs the screen: `ingenic-x1600-drm` for the controller, `panel-hiby-lg35583` for the panel and `pwm-ingenic-x1600` with `pwm-backlight` for the backlight. Verified: console and RGB565 colours (red, green, blue bands), the panel's power cycle (`echo 4`, then `echo 0`, to `/sys/class/graphics/fb0/blank`) and a brightness sweep (100, 10, 0, 60), by eye; 5 boots of three screen off/on cycles each, after the last fix, without a timeout.
  - **Controller (0x13050000, intc 31):** FRM_DESC (0x1000) takes the address of a frame descriptor (next, frame address, stride in pixels, format in bits 22:19 of word 3: 2 RGB565, 4 32-bit; bit 17 of word 4 as the vendor sets it) and FRM_START (0x1004) starts the fetch. The driver keeps two self-linked descriptors and flips by writing the other's address to FRM_DESC and setting FRM_START, as the vendor driver does; the controller takes it at the end of the frame. Flipping by relinking the shown descriptor instead completed a frame late: r1player drew into a page still on screen, and scrolling tore at mid-screen (seen 2026-10-23). CTRL (0x2000) bit 4 stops at the end of the frame; ST (0x2010) bits 7 stopped, 8 underrun, 17 descriptor fetched, CLR_ST (0x2008) and INT_EN (0x200c); COM_CFG (0x8000) the interface (1 TFT) and dithering; TFT timings at 0x9000–0x900c (sync length or start in bits 27:16, total or end in 11:0) and TFT_CFG (0x9010: polarities in bits 10:7, colour order 2 (BGR) in 21:19 and 18:16, as stock; MODE in 2:0 stays 0 (888) although the panel has 18 data lines: the 666 mode (1) gave wrong colours and a grainy picture, seen 2026-10-25, so the panel takes the top six bits of each colour; the driver takes the order from the panel's bus format, `BGR666_1X18`). The stock timings, read back from the registers: 552×827 total, 24/24/24 horizontal and 8/14/5 vertical (back porch, front porch, sync), 28 MHz from MPLL ÷ 50 (61 Hz).
  - **Two traps, each found by a failure:** a status bit is only set while its interrupt is enabled, so polling for "stopped" with INT_EN cleared never succeeds; the first driver's stop at probe always timed out, and when the stop landed after the first start (1 boot in 4) the controller stayed stopped and every vblank wait timed out. And a status bit set just before its interrupt is masked keeps the line raised: a handler that only cleared enabled bits returned IRQ_NONE until the kernel disabled IRQ 31 ("nobody cared", about 5 s after boot, when vblank turns off). The driver now waits for the stop through the interrupt, clears every pending bit in the handler, and clears a bit when it masks it.
  - **Pins:** the panel takes 18 bits on the six most significant lines of each colour of the 24-bit bus (PA2–PA7, PA10–PA15, PA18–PA23, plus PA24–PA27 for clock, DE and syncs), leaving PA0/PA1 to the panel's SPI and PA16/PA17 to the touch panel. No mainline group matched, so patch 0024 adds `lcd-18bit-msb`.
  - **Panel:** R1s ship with an LG35583 or an ST7701S; ADC channel 3 tells them apart (below 1000 mV: LG35583). This unit reads 0 mV. Both are set up over a bit-banged 3-wire SPI (SCK PA0, MOSI PA1, CS PA30, reset PA31, active low), here `spi-gpio`. The LG35583 takes 16-bit words: `0x20` and a register's high byte, `0x00` and its low byte, `0x40` and a data byte (`hiby,lg35583`, sequence from the vendor driver; its controller is unidentified). The ST7701S variant would need an entry in mainline's `panel-sitronix-st7701` and a way to pick the panel at boot; neither exists.
  - **Backlight:** PC0 is channel 0 of the X1600's own PWM controller (0x134c0000), not a TCU channel (`pwm-jz4740`). Per channel: a divider of 2^n (CCFG, 0x40 + 4n) and a waveform word (WCFG, 0x80 + 4n: the HIGH count in bits 31:16 and the LOW count in 15:0, whatever the starting level; INL (0x24) only picks which comes first, manual 13.4 and its figure), loaded by UPT (0x10) while the channel runs (BUSY, 0x14); ENS/ENC (0x00/0x04) switch channels on and off, EN (0x08) reads them back; IDL (0x28) holds the idle level. Neither count may be zero, so 0 and 100% switch the channel off with the idle level set, and the prescaler may only change with the channel off. The first driver read bits 31:16 as "counts at the starting level", which made inverted polarity a phase-shifted normal waveform; since 2026-10-25 it uses the waveform callbacks, verified with `CONFIG_PWM_DEBUG` (backlight steps exact; inverted 250 µs of 1 ms on channel 1 gives INL 0, LOW 9375 then HIGH 28125). Clock: EPLL, 300 MHz. Stock runs it at 30 kHz; channels 1 and 2 (PC1, PC2) are the red and blue LEDs, not described yet.
  - **The controller halts after an underrun (fixed in `boot.sh`, 2026-10-23):** left scanning out stock's frame through the jump, it was found halted at probe on about 1 boot in 13 (6 of 79; 8 of 100 in the measurement below): register 0x2004 (DC_ST, the raw status: bit 0 WORKING, 1 SRD_END, 2 SRD_START, 3 SRD_WORKING, 7 STOP_SRD_ACK, 8 TFT_UNDR, 17 DISP_END; 0x0f running, 0x06 or 0x20006 stopped) reads 0x10f, no descriptor is fetched (IRQ 31 counts 0, vblank waits time out) and it ignores the end-of-frame stop, the quick stop (CTRL bit 1) and SRD_CHAIN_START until a reset. Bit 8 is TFT_UNDR, the underrun flag, whose interrupt stock enables; the likely cause is the memory traffic of `r1jump`'s copy and the new kernel's start-up starving the scan-out (not proven). A measurement over 100 boots, with the probe's stop written at a random point of the frame and its phase logged, found the 8 halted controllers already halted before the stop (no frame started in the 40 ms before it): the stop does not cause it, and timing it (an earlier attempt, written 5 ms after a frame start) did not help, 2 halted in 40. Stopping the controller on the stock side before the jump: 100 boots of 100 good (2026-10-23), the state a cold boot from the SPL would also leave. The driver logs "The controller did not stop after an underrun" if it finds one (it only stops a controller DC_ST reports as working). While the LCD clock is gated (screen blanked) every LCD register reads 0x80: the clock also gates register access.
  - **Not done yet:** 32-bit (XRGB8888) frames, untested; the emulated fbdev's memory is coherent DMA memory, uncached on MIPS (r1player scrolls smoothly on it, by eye); the 1.5 MB of stock pages stay reserved after the handover; `clk_ignore_unused` is still in `bootargs`.
- **r1player on mainline (2026-10-23):** the menus, touch, keys, power key (screen off and on) and playback work, by eye and ear, with patches 0033 and 0034 and the r1player changes of the same day. How it runs:
  - **Files:** it needs glibc 2.22 and the stock font, which don't fit in the image (the image waits in stock's RAM `/tmp` while `r1jump` loads it, so 24 MB would run stock out of memory). `kernel/tools/sdsync.sh`, run with the R1 on stock, puts r1player, the stock `/lib` files it links against and `default.otf` in `/.r1-mainline/` on the card (copied on the R1 itself, so no HiBy file passes through the Mac); the initramfs linked `/lib` and the font path there until 2026-10-24, when they moved to the stock root filesystem in flash (below); the card copies remain the fallback. A static musl build failed to link (zig's `compiler_rt` missing math symbols, 2026-10-23) and wasn't pursued.
  - **The init script** mounts the card on `/mnt/sd_0`, unbinds fbcon from the console (it would draw kernel messages over the player), runs r1player in a restart loop with its log in `/tmp/r1player.log`, and keeps the serial shell. `/usr/data/r1player` is in RAM, so the index is rebuilt at every boot.
  - **Driving it without anyone at the R1:** r1player reads commands from the named pipe `/tmp/r1player.ctl` (`play PATH`, `key playpause|next|prev|volup|voldown|power`, `tap X Y`, `swipe X0 Y0 X1 Y1`) and writes its state to `/tmp/r1player.status`, under either kernel (`player/src/ctl.rs`).
  - **Trying a new build without `sdsync.sh` (2026-10-23):** `r1sh.py --push target/mipsel-unknown-linux-gnu/release/r1player /r1p-NAME` (3 MB in about 6 s), then `mount --bind /r1p-NAME /mnt/sd_0/.r1-mainline/r1player; kill $(pidof r1player)`: the init loop restarts it from the bind-mounted copy. Nothing is written to the card, and a reboot undoes it. Push each new build under a new name: pushing onto the one running fails (text file busy), and `umount` of the busy bind fails too, but a second `mount --bind` stacks on top and takes effect. For a screenshot, run `r1player --shot /tmp/fb.raw` and pass the file back through `gzip -c | base64` between marker lines; the first line of `r1sh.py`'s output starts with the shell prompt (`/ #`), so don't anchor the marker match at line start.

- **Bluetooth (2026-10-23, after the watchdog patches: the serial binding, the X1600's UARTs, the R1's Bluetooth node and `serial: 8250_ingenic: start the X1000 UART from 16 clocks a bit`; `kernel/initramfs/r1-bt`):** pairing, connecting and A2DP playback to a headset work under mainline (an OpenRun Pro 2, SBC at 48 kHz: a 440 Hz tone through `bluealsa-cli open`, twice in a row, heard). r1player's side (its Bluetooth page: `bluetoothctl` on a pseudo-terminal, which needs `/dev/pts`, and output through `bluealsa-cli open`) and pairings that survive a restart were verified on 2026-10-23 with the same headset: it reconnected by itself after a restart, its PCM present about 30 s after boot. The patch resets UMR to 16 and UACR to 0 at probe (sent upstream scoped to `ingenic,x1600-uart`; Schaller objects that UMR also exists on the X1000 and JZ4780 and that this works around a boot loader, not an X1600 property, 2026-10-24, and the manuals partly bear him out: the same UMR/UACR pair sits at 0x24/0x28 on the JZ4725, JZ4740, JZ4755, JZ4760, X1000, X1830, X2000 and X1600, and the 8 was left by earlier software (the stock boot loader sets 8 on its console UART2 even on a cold boot; UART1 and UART3 read 0).   - **Driver:** mainline `brcmfmac` and cfg80211 built into the card kernel only (`kernel/r1-card.config` on top of `r1.config`; `build.sh` builds the two kernels in `build-arm64` and `build-card`): they don't fit the 5 MiB flash image, the flash kernel doesn't need them, and its device tree has the Wi-Fi nodes disabled (`fdtput` in `build.sh`; "USB lost at some starts" below). They were modules at first, and `CONFIG_MODULES` was one of the changes after which some starts lost USB. Firmware from the system image's `/lib/firmware/brcm/`, the kernel's fallback path: stock's `fw_bcm43438a1.bin` as `brcmfmac43430-sdio.bin` (it reports `version 7.45.96.123`) and `nvram_ap6212a.txt` as `brcmfmac43430-sdio.txt`. "No clm_blob available" and "failed to load regulatory.db" are expected: stock has neither. At boot `brcmfmac` finds the chip before `/rom` is up and fails on the firmware; init then powers the chip down (below).
  - **Trap: the SD clock's low-power mode (patch 0059).** Above 25 MHz `jz4740_mmc` turned on MSC_LPM's low-power mode, which stops the clock while the bus is idle, and an SDIO card needs the clock to signal an interrupt. `brcmfmac` puts the chip to sleep when the bus has been idle (40 ms after the firmware started) and wakes it with a clock request whose completion comes by interrupt, so most attaches timed out ("brcmf_bus_started: failed: -145", "dongle is not responding"; 1 to 5 of 6 attaches worked). Found with `CONFIG_BRCMDBG` and `debug=0x20114` (the wake request stayed `PENDING`), confirmed by clearing bit 0 of 0x13450040 with `devmem` (8 of 8). Ruled out first: lost SDIO flags in the interrupt handler, and the integrated DMA (5 of 6 with it, 4 of 6 in PIO, through a test switch).
  - **Trap: SDIO writes glued from several frames (patch 0054).** Once connected, the first DNS or TCP traffic ended the bus: `mmc_submit_one: CMD53 sg block write failed -145`, then `brcmf_sdio_isr: failed backplane access` every 5 s, and `ip link set wlan0 down` and the restart's driver shutdown hung for good. `brcmfmac` glues frames into one multi-block write whose segments end inside a block; the integrated DMA times out on that (the SD card only ever hands it whole blocks). With the DMA switched off by a test parameter, 5 rounds of DNS, HTTP and pings went through; with it on, the bus died in the first round, twice. The driver now sends a transfer with a segment that isn't a whole number of blocks through PIO: 10 rounds, then three on/off cycles, with no bus error. Large single-frame pings went through the DMA either way (597 of 597).
  - **Userspace:** `initramfs/r1-wifi on` binds MSC0, whose probe powers the chip up (its `mmc-pwrseq`) and lets `brcmfmac` take it, starts the stock `wpa_supplicant -Dnl80211` (from the system image, `/rom/usr/sbin`, with its control socket in `/tmp/wpa`) on a RAM copy of `/.r1-mainline/wifi.conf` (wpa_supplicant's format; it holds the network's password and stays on the card, never in the repository), then busybox `udhcpc` with `initramfs/r1-dhcp`, which sets the address, route and name servers and writes `/tmp/wifi-address`. `r1-wifi off` stops both and unbinds MSC0, which holds WL_REG_ON low (each step under `timeout 5`); init runs it at boot, so the chip is off until something turns Wi-Fi on. Unbinding matters: loading the driver again into a chip still running its firmware connected to nothing (empty scans, `DISCONNECTED`). `udhcpc` makes one quick try, then retries every 3 s (`-A 3`): its first discover goes out before the association. Verified 2026-10-25 on the built-in driver: three on/off cycles, each with an address 4 s after `on`, 3 of 3 pings to the router and DNS answering; 12.9 MB available with Wi-Fi on. Card writes (`dd`, 32 MB) and `adb push` (3.9 MB/s) ran as fast with Wi-Fi scanning as without.
  - **The clock:** the R1 has no RTC that keeps time (`/sys/class/rtc` is empty) and starts at 1970. `r1-dhcp` sets it from a web server's `Date:` header once the address comes (`/tmp/wifi-clock`), tried 5 times 3 s apart. busybox (Debian's static 1.35) has no NTP client; its `wget` crashes (SIGSEGV) looking a name up, a static glibc not being able to load its resolver, and with `-T` whatever the address; `nslookup` works. So it looks `www.google.com` up with `nslookup`, then `timeout 10 wget -S --header "Host: …" http://ADDRESS/`.
  - **r1player's Wi-Fi page (2026-10-25):** it turns Wi-Fi on and off with `r1-wifi`, joins and forgets networks through wpa_supplicant's control socket, and saves them to the card's `wifi.conf`. Verified on the R1: on, scan, a WPA2 network joined with its password, saved to the card, an address and the clock; off and on again rejoining it by itself; an off then an on queued behind it. It gives `r1-wifi` 30 s, and when wpa_supplicant hangs (below) says the R1 needs a restart.
  - **Trap: the interrupt handler cleared a finished DMA transfer's flags (patch 0054, 2026-10-26).** Seen first on 2026-10-25 after six on/off cycles in five minutes: connected, `brcmf_sdio_readframes: read 1484 bytes from channel 2 failed: -145`, then `brcmf_sdio_isr: failed backplane access` every 5 s for good; wpa_supplicant, `ip link set wlan0 down` and the SDIO kworkers stuck in D (`__mmc_claim_host`, `mmc_wait_for_req_done`, `devinet_ioctl`), so `r1-wifi off` never returned, and only a restart helped. The on/off cycling played no part. **Reproducer:** `r1-wifi on`, then from a computer on the same network UDP datagrams of random sizes (1 to 1472 bytes) at 1000 a second to the R1's port 9 (a few lines of Python): the bus died in 10 runs of 10, most within a minute (the fastest in 10 s), on a read (`read 890 bytes …`) or a write (`brcmf_sdio_txfail`). **How it was found:** a side build logged the MSC registers on every timeout and error. Each time the first failed request was a CMD53 carried by the integrated DMA (2 × 512 bytes read, or 1 × 512 written) that timed out after 5 s with every byte moved (DMADA at the end, DMALEN 0) and no DATA_TRAN_DONE, and an SDIO interrupt had come during it. With the integrated DMA off at run time (PIO for everything), 150 s at 1000 to 1500 datagrams a second went through clean, and switching it back on in the same boot killed the bus again. Then the hard handler recorded the controller at the SDIO interrupt: 50 µs into a 2-block read MSC_STAT already had DATA_TRAN_DONE and DMAEND, but MSC_IFLG no longer had DATA_TRAN_DONE after the handler's write. That write clears the flags of masked interrupts, all but the few the driver polls, so it also wrote 1 to DMA_DATA_DONE (bit 31), which the integrated DMA sets with DATA_TRAN_DONE and DMAEND as a transfer ends. Checked on its own after a DMA read: writing 1 to bit 31 alone took MSC_IFLG from 0x80012001 to 0x00002000 and MSC_STAT from 0x1f011140 to 0x1f000140, so clearing it clears DATA_TRAN_DONE and DMAEND too. An interrupt between the end of a DMA transfer and the worker's poll (an SDIO interrupt, under traffic) therefore left a complete transfer to time out. PIO transfers never set DMA_DATA_DONE. It is rare per transfer (14 of 2,699 DMA transfers saw an SDIO interrupt in one run) but traffic makes thousands. **After the timeout** the chip holds DAT1 low (its interrupt, function 1 pending in CCCR 0x05; still low with PB15 switched to a GPIO input, so the chip drives it) and no data transfer finishes any more, PIO ones included: brcmfmac's 4-byte read of its interrupt status every 5 s, the data arriving but never DATA_TRAN_DONE. CMD52s still answer, CCCR 0x07 still says 4-bit, and resetting the controller (MSC_CTRL bit 3) changes nothing; why the chip stays so is not known. **Ruled out** on the way, each still failing: CMDAT's SDIO_PRDT (bit 17); keeping the bus clock running between commands, as Ingenic's driver can (`sdio_clk`); sampling on the clock edge (LPM 0x80000000, Ingenic's setting); masking the SDIO interrupt for the length of each DMA transfer (failed once, not explained: the SDIO core re-enabling it meanwhile is possible); skipping the handler's write once the bus was stuck (no recovery). **Fix:** the handler leaves DMA_DATA_DONE and WR_ALL_DONE alone. With it, 600 s at 1000 datagrams a second: 191,533 DMA transfers, 2,601 of them with an SDIO interrupt, no error; then 40 on/off cycles in 40 minutes (53 `on`s: every third cycle also an off and an on 0.4 s apart, as on 2026-10-25), each with 45 s of those datagrams at 800 a second, 2 MB sent from the R1 over TCP and 10 pings, all through, no SDIO error, every `off` in 0.61 to 0.63 s. The SD DMA notes above that DMA_DATA_DONE "never came" (even unmasked, `iflg 00002000`) and DMAEND came only sometimes were taken with this handler in place; they may be this bug rather than the hardware. Whether patch 0054's SDIO write trap above was this too (same signature, and its PIO workaround cuts the DMA transfers) is untested.
  - **Trap: `r1-wifi off` took 5.7 s (patch 0060, 2026-10-26).** The step that ran out its `timeout 5` was the unbind of MSC0: `/proc/PID/stack` of the unbinding shell sat in `sdio_release_irq` (brcmfmac's remove, reading the card's interrupt enables with a CMD52) for 5.1 s. `jz4740_mmc_remove()` masked every interrupt and reset the controller before `mmc_remove_host()`, which removes the card and lets its driver send its last commands; that CMD52 had finished (MSC_STAT's END_CMD_RES) but MSC_IMASK read 0xffffffff and it waited out the 5 s request timeout. MSC_STAT can still show IS_RESETTING after `jz4740_mmc_reset()` returns, so the reset most likely ends after the request unmasked END_CMD_RES and undoes it. The patch removes the host first. `r1-wifi off` now takes 0.65 s (three in a row), without "Terminated".
- **PMIC (stage 5, 2026-10-23):** the AXP2101 at 0x34 on I2C0 (PA28/PA29, function 2; intc 61) is added to mainline's `axp20x` drivers (patches 0017–0019; nothing upstream as of 2026-10-23), with the register map of HiBy's GPL driver. Under the stock firmware DCDC1–4 (3.3, 1.1, 1.8, 1.2 V), ALDO2 (3.3 V, touch), ALDO3 (1.1 V, consumer unknown), ALDO4 (3.3 V, headset remote), BLDO1 and BLDO2 (2.8 V, LCD vcc and vccio) are on; ALDO1, DLDO1/2, CPUSLDO and DCDC5 are off. The R1's DT describes only the rails that are on, each at its stock voltage and always-on unless a driver claims it: the regulator core switches off any described rail no driver claims, 30 s after boot. The touch driver claims no supply; the panel driver switches BLDO1 and BLDO2 (bits 4 and 5 of 0x90 clear with the screen off, verified 2026-10-23). Verified: a first boot with no constraints read every voltage back as stock, and with constraints registers 0x80–0x9a stay byte-for-byte stock past the 30 s cleanup.
  - **Power-off** is bit 0 of COMM_CFG (0x10), not `AXP20X_OFF_CTRL`: `poweroff -f` turns the R1 off. Turning it on again takes a press of about a second (REG 0x27, set to 1 s by stock); a short tap does nothing.
  - **Interrupt (PB23, active low):** open drain with no pull-up on the board, so the DT enables PB23's internal pull-up. Without it PB23 reads 0 as an input, the level interrupt never stops and the boot stalls after the CW2015 probe (seen 2026-10-23). The stock kernel never arms it (0 interrupts under stock; PB23 stays on a pin function).
  - **USB power (patch 0020, `x-powers,axp2101-usb-power-supply`):** `/sys/class/power_supply/axp20x-usb` reports online/present (bit 5 of 0x00) and the input current limit (0x16: 100, 500, 900, 1000, 1500, 2000 mA; stock sets 500). Verified 2026-10-23 by unplugging and replugging: one VBUS_REMOVAL and one VBUS_PLUGIN interrupt, `online` 1 → 0 → 1, and the CW2015 (whose `power-supplies` points here) Full → Discharging → Full within its poll interval.
  - **Charger (patch 0021, `x-powers,axp2101-battery-power-supply`):** programs 0x61–0x64 from the R1's `simple-battery` node (700 mA, 4.4 V, 100 mA termination and precharge: the stock values; 0x64 selectors 1–5 are 4.0, 4.1, 4.2, 4.35, 4.4 V, one more than the AXP717's) and reports the real charge state from 0x01 as `/sys/class/power_supply/axp20x-battery`, without a capacity. Verified 2026-10-23: 0x61–0x64 and 0x16/0x18 byte-for-byte stock after boot; status Full on USB, Discharging unplugged, Charging on replug. HiBy's driver advertises a 4.35 V design voltage but programs 4.4 V; the DT follows the register.
  - **Not handled yet:** the PMIC's own fuel gauge (uncalibrated: stock reads 0% from it), the input limit (0x16, left at stock's 500 mA) and the TS pin.
- **Battery gauge:** the CW2015 at 0x62 on I2C0, with the battery profile from the stock `cw2015.sh`, works through mainline's `cw2015` (`/sys/class/power_supply/cw2015-battery`: 4.335 V, matching stock). It rewrites the profile at every boot ("Replacing stored battery profile"), which restarts its estimate: capacity reads 1% for a few seconds, then settles (98% where stock said 100%). Its status comes from the AXP2101's USB supply: Charging or Full on USB, Discharging otherwise.
- **USB gadget after a replug (patch 0005; works with an active bus since 2026-10-23, a replug after the host suspended the bus is untested):** after an unplug `dwc2` saw the replug ("new device is high-speed") but every enumeration failed with `dwc2_hsotg_enqueue_setup: failed queue (-11)`. The session end leaves the gadget in `lx_state` L3, and nothing returns it to L0: the USB reset handler only reinitialises a gadget that is still `connected`, and only an external VBUS notifier (`usb_gadget_vbus_connect`) would otherwise, so EP0 refuses its setup request (-EAGAIN). The patch restarts the gadget on the session-request interrupt that the replug raises, as `dwc2_hsotg_vbus_session()` does; verified by a replug that brought the serial shell back without a reboot. Not upstream (master had the same code on 2026-10-23).
- **USB-C role (patch 0023):** the TCS1421 Type-C controller has no bus; CFG0 (PA9) and CFG1 (PB24) set its role: 00 sink, 10 source, 01 strong DRP, 11 normal DRP. The stock firmware leaves both high (DRP), so a plug-in attaches as a source about half the time: the Mac then supplies no VBUS (seen as a first replug that does nothing and a second that works), and on stock the controller comes up as a USB host. The DT holds both low with `gpio-hog`s: sink, every replug works (3 of 3, 2026-10-23). Host/OTG later needs the pins switchable again, `dwc2` in OTG mode with the host side built, and a VBUS regulator on PC24 (the stock tree's `ingenic,drvvbus-gpio`). The stock `cw2015.sh` also names PA9 as the gauge's interrupt; mainline's `cw2015` uses none.
- **Watchdog (TCU at 0x10002000; tested 2026-10-23 by arming it by hand with `devmem` on a mainline boot):**
  - **Reset compare:** the low half of TDR (0x00). With 320 ticks there the R1 reset after about 10 s; with 320 in the high half and 0xffff in the low half it was still up after 46 s. `r1jump` also writes 2/3 of the timeout into the high half, as the stock driver does; what that half does is unknown.
  - **Clock:** EXCLK / 512 = 46875 Hz, divided by 1024 = 45.8 ticks a second, when TCSR selects the "RTC" input. OPCR (0x10000024) bit 2 picks that source; it reads 0 under both kernels, and the stock clock tree calls the mux `mux_wdt` with parent `ext_div_512`. The RTC module itself runs from the 32768 Hz crystal (`gate_rtc`).
  - **Feeding:** setting TCSR (0x0c) bit 10 zeroes the counter, as the stock driver's ping does. Writing 0 to TCNT (0x08), as mainline's `jz4740_wdt` pings, doesn't: armed for 640 ticks, the R1 reset after about 16 s.
  - **Mainline driver (patches 0035–0039; verified 2026-10-23):** `jz4740_wdt` with a TCSR-bit-10 ping for `ingenic,x1600-watchdog`, and it keeps a watchdog it finds running (`WDOG_HW_RUNNING`), so the kernel feeds it until userspace opens `/dev/watchdog0`. The CGU's "rtc" is a mux on OPCR bit 2 between `ext/512` and `osc32k`. After boot `clk_summary` shows `ext/512` → `rtc` 46875 Hz → `wdt` 45 Hz, and TDR reads 0xE1 (5 s). Booted with `r1jump` armed for 20 s, the R1 was still up at 30 s. The TCU node also brings in `ingenic-timer`, whose clocksource (on "ext") loses to the OST.
  - **Trap, the CGU's parent order:** the Ingenic CGU core registers clocks in ID order and finds a clock's parents among those already registered. A parent with a higher ID than its child gives the clock core NULL parent names, and the kernel hung before its console. Parents need lower IDs, as on the JZ4770: OSC32K is 1, and EXT512 and RTCLK come last.
  - **Not armed in the flash-boot chain (found 2026-10-25):** the stock SPL doesn't start the watchdog and the driver only keeps one it finds running, so after the flash install TCER read 0 and a frozen kernel stayed frozen (a panic from `echo c > /proc/sysrq-trigger` left the last r1player frame on screen until a power-button restart; probably what the black-screen boots of the SD DMA work were). Init now runs busybox `watchdog -T 10 -t 2 /dev/watchdog` right after mounting `/dev`, which starts it: the same panic reset the R1 by itself, back on ADB about 15 s later. A flash kernel with this init would also cover the kexec into a card kernel that hangs before its driver probes (the hardware keeps running across kexec).
  - **The last boot's log (ramoops, 2026-10-25):** the card kernel reserves 64 KiB at 0x03ff0000 for ramoops (console and oops) and init mounts `/sys/fs/pstore`. After the panic and watchdog reset above it was empty while the flash kernel was #98, which runs first and doesn't reserve that memory. With a flash kernel built from the same device tree (installed 2026-10-25) it works: after a deliberate panic, `dmesg-ramoops-0` held the card kernel's log up to "Kernel panic - not syncing: sysrq triggered crash", and `console-ramoops-0` the flash kernel's console of the boot after (its reset cause 0x2 and the kexec). `rm /sys/fs/pstore/*` clears them.
  - **Trap, the TCU clocks' reset:** registering the TCU clocks reset each channel's TCSR to divider 1, the watchdog's included (patch 0036 skips it when TCER is set). Without that, the watchdog `r1jump` armed for 120 s counted 1024 times faster and reset the R1 about 3 s after the jump, with nothing on screen to show it.
- **SD card detect is PB22** (falling edge, `mmc-insert-detect` in the stock kernel's `/proc/interrupts`); the DT still uses `broken-cd`.
- **Bus numbers changed:** with I2C0 enabled, the DAC's GPIO bus is `i2c-0`, I2C0 is `i2c-1` and the touch panel's I2C1 is `i2c-2`.
- **Testing tools in the initramfs:** busybox `devmem` (register reads and writes; `debugfs` mounts on `/sys/kernel/debug` for `clk_summary`, `gpio` and `pwm`) and `i2cget -f -y BUS ADDR REG` (bus numbers just above); `tinymix` and `r1tone [freq [dBFS [seconds [rate [channels]]]]]` (`kernel/initramfs/r1tone.c`), against a tinyalsa master commit from 2026-09-29: v2.0.0's `pcm_state()` hands the kernel a stale `appl_ptr` on MIPS (no mmap of the PCM status), so every write was dropped and nothing played. `r1sh.py --push LOCAL REMOTE` copies a file over the serial shell; the initramfs has no `/tmp`, so push to `/`. `r1sh.py` waits 60 s at most per command, so start anything longer in the background on the R1. Record input events with `timeout N cat /dev/input/eventN > file` and decode afterwards: busybox `hexdump` buffers its output and loses it when `timeout` kills it. While r1player runs this records nothing: it grabs every input device (`EVIOCGRAB`); read the keys' ADC level from `/sys/bus/iio/devices/iio:device0/in_voltage0_raw` and the GPIO keys from the port's PIN register (`devmem 0x10010200`, port C) instead.
- **Command line:** taken from the device tree's `bootargs` only (`MIPS_CMDLINE_FROM_DTB`); with a built-in one (as `cu1000-neo_defconfig` has), MIPS ignores `bootargs`.
- **Boot marks:** the `DEBUG` patch paints a 16-row stripe on framebuffer page 0 at each milestone: black at row 352 (first instruction of `kernel_entry`), grey at 376 (BSS cleared), then `start_kernel` steps from row 400 (n = 0..8) and `setup_arch` steps (n = 10..16), every 24 rows. This is how the PRId panic was found. Each mark also writes `0xb0070000 + n` to 0x03ff7ffc, the end of ramoops' second dmesg record (written only by an oops dump), which a watchdog reset leaves alone: after a start that fell back, `devmem 0x03ff7ffc` on the flash kernel names the last mark reached (write 0 there first). `r1_note(n)` writes only that word, for steps between the stripes (more stripes would reach page 1, which holds the display's frame descriptor).
- **Kernel log after the reset:** mostly lost. `__log_buf` (phys 0x976134) lies past the stock kernel's image, but the stock system reuses that memory before ADB comes up.

- **Jumping to our own code works (2026-10-23).** `r1jump` loaded `kernel/tools/fbpaint` (176 bytes at `0x80010000`), which painted colour bands over the whole screen; the watchdog brought the R1 back about 15 s later.
  - **Why the first attempt failed:** the stub, its params and the page list were written through cached KSEG0 but executed and read through uncached KSEG1, so the CPU ran stale RAM (254 of the stub's 276 bytes hadn't reached it). `r1jump` now writes them back from L1 and L2 first, and a dry run prints `uncached view differs: stub 0, params 0, list 0 bytes` to show it.
  - **The screen is a debug channel:** the LCD controller refreshes continuously at 60 Hz (the `jzfb` interrupt), straight from the framebuffer at physical `0x02600000` (480×800 RGB565, 960-byte lines, two pages). A new kernel can paint progress there with uncached stores and no display driver, as long as it leaves the LCD controller and its clocks alone. Writes from Linux through `/dev/mem` show up too.
- **Debugging without serial (superseded):** the user has no serial adapter. What works instead: the boot-mark stripes and the framebuffer console on screen, then the USB serial shell once the kernel is up. Recovering a crashed kernel's log from RAM after the reset does not: DRAM keeps its contents through a watchdog reset and the SPL, but the stock boot reuses free memory before ADB is up. `kernel/tools/ramtest.sh` measured it on 2026-10-22: 2 of 1044 marker pages left when checked 4 minutes after boot, 0 of 1040 when checked as soon as ADB came back (7 s).
