# Kernel: boot chain, stock-kernel facts and the mainline port

Read this before working in `kernel/` or on anything that boots a kernel
other than the stock one. Observed on the R1 with patched firmware 1.6 on
2026-10-22 unless marked otherwise.

## Boot chain (verified)

- **Bootloader:** `mtd0` holds only a U-Boot SPL (`U-Boot SPL 2013.07-g3fccbcd`, built 2025-01-16). It uses about 16 KB of the 512 KB partition, the rest is erased. It boots Linux directly (falcon mode); there is no full U-Boot, no U-Boot console and no display init, so nothing lights the screen before Linux.
- **Kernel slot:** the first bytes of `/dev/mtd5` (`ota`) read `ota:kernel`, space-padded. The SPL also knows `ota:kernel2`, which boots `kernel2` + `rootfs2`.
- **Slot choice and the recovery (read from the SPL dump and the recovery rootfs, 2026-10-23):** the SPL boots `kernel2` + `rootfs2` when `ota` reads `ota:kernel2` *or* when ADC channel 0 reads 1600–1800 mV at power-on, which is Volume Up held (1.65 V). The second slot is not a copy of the first: it is HiBy's recovery system (kernel built 2024-11, against 2026-01 for `kernel`; `rootfs2` is 24 MB, `rootfs` 45 MB). Its `recoveryd` mounts the SD card, loop-mounts `r1.upt` or `update.upt`, sets `ota:kernel2`, writes the update's `xImage` and `rootfs.squashfs` into `kernel` and `rootfs` (`/etc/ota_bin/local_ota_update.sh`: it writes the slot `ota` doesn't name, so never itself), then sets `ota:kernel` (`/usr/bin/bootmode.sh Normal`) and reboots. Settings → Firmware update goes through it. So stock can be restored from the card without the first slot being bootable, as long as `uboot`, `kernel2`, `rootfs2` and `ota` stay as they are. To look inside: `mount -t squashfs -o ro /dev/mtdblock_bbt_ro4 /tmp/r2` from stock.
- **How the SPL loads the kernel:** U-Boot's `spl_parse_image_header`: a legacy uImage is loaded by its header's load address, entry and size; there is no checksum check and no size limit beyond the 5 MB partition. Without the uImage magic it loads 768 KB to 0x80100000. The SPL itself runs from 0x80001000 (file offset 0 of `mtd0`); disassemble it at that address.
- **Command line:** baked into the SPL, one variant per slot, differing only in `root=/dev/mtdblock_bbt_ro2` vs `ro4`. Running: `console=ttyS2,3000000n8 quiet mem=64M@0x0 init=/linuxrc flashtype=nand root=/dev/mtdblock_bbt_ro2 rootfstype=squashfs ro`.
- **Kernel image:** legacy uImage (`file firmware/stock/xImage`), load and entry `0x80F00000`, a self-decompressing gzip payload of 3.7 MB. The kernel partitions (`mtd1`, `mtd3`) are 5 MB each.
- **Serial console:** UART2 at 3,000,000 baud. Where its pads are on the board is not known.
- **USB boot mode (seen 2026-10-23):** the R1 reset while Next (PC28) was held came up as `Ingenic USB BOOT DEVICE` on the Mac (USB 0xa108:0xeaef), the X1600 boot ROM waiting for a host instead of loading the SPL: Next's pin is evidently a boot-select pin. Holding Power until it switched off, then switching on without Next, booted stock normally. So never ask for Next to be held while the R1 starts. It is also a route that doesn't depend on the flash. `kernel/tools/usbboot/` boots a kernel through it into RAM, writing nothing to flash (`usbboot.py`'s docstring has the commands; done twice on 2026-10-23). What it relies on:
  - **Protocol** (Rockbox `utils/jztool/src/usb.c` and `x1600.c`): vendor requests 0 GET_CPU_INFO (bmRequestType 0xC0, answers "X1600"), 1 SET_DATA_ADDRESS, 2 SET_DATA_LENGTH, 3 FLUSH_CACHES, 4 PROGRAM_START1, 5 PROGRAM_START2 (0x40; the 32-bit argument split over wValue high and wIndex low), data over bulk EP 1. `jztool` builds on the Mac against Homebrew's libusb (override its `/usr/local` paths) and knows the R1 as `hibyr1`.
  - **DDR set-up:** the R1's RAM (ESMT M54D5121632A) is LPDDR2, not DDR2 (type 2 in the SPL dump at 0x4060). Rockbox's `usbstage1` for the R1 (`hibyr1native`, in the unmerged Gerrit chain 7833…7734, DDR in change 7836) carries the stock SPL's DDR parameters word for word; it runs at 0x8000a000, writes a result block (magic 0xc0def00d, rc) at 0x8000f000 and returns to the boot ROM. It builds with Debian's `mipsel-linux-gnu-gcc` 12 in the `r1-mainline` image given `-mno-abicalls -fno-pic -no-pie -Wl,--build-id=none`, an empty `gnu/stubs-o32_soft.h` and `elf32-tradlittlemips` in place of `elf32-littlemips` in its linker scripts.
  - **Clocks:** `usbstage1` sets only MPLL and the DDR clock; stock runs CPCCR 0x9A094410, APLL 0x02E049CD, MPLL 0x0AF0C9CD, EPLL 0x019051CD (read with `devmem` on stock). EPLL feeds the backlight PWM and I2S, so a kernel started straight after `usbstage1` needs APLL, EPLL and the bus dividers set first.
  - **Entering it without Next** (from Ingenic U-Boot 2013.07, [k1-debian/u-boot](https://github.com/k1-debian/u-boot) `arch/mips/cpu/xburst/usb_boot.c`): `devmem 0x100000cc 32 0x42575302; sync; reboot -f` from mainline (its reboot is a watchdog reset) brings the boot ROM up on USB within a second (verified 2026-10-23). The value survives until a reset reads it; `stage2` clears it, so the next reset boots from flash. A background `(sleep 1; reboot -f) &` in `adb shell` dies with the shell and never reboots.
  - **Measured:** `usbstage1` reports rc 0 (DDR set up), the 11.5 MB kernel goes over in 5.6 s and reads back identical, and the kernel boots: its serial shell comes up.
  - **What a cold boot lacks (2026-10-23, cold-boot `dmesg` and `clk_summary` compared with a boot through `r1jump`):** the PWM, LCD and MSC1 clock muxes are at their reset value, SCLK_A (1104 MHz), where stock set PWM to EPLL (PWMCDR 0x80000000) and LCD and MSC1 to MPLL. The backlight then flickered visibly. The SD card fails at every try (`mmc0: Card stuck being busy!`, error -145), so nothing on the card (r1player, `adbd`) starts. Bluetooth times out (`command 0xfc18 tx timeout`), as expected without the 32 kHz clock on PC26. Not yet known: whether the card fails from its clock or from something else stock sets (a PMIC rail, a pin).
- **Reading the bootloader:** `cat /dev/mtd0` works over ADB (read-only use only). A dump is in `firmware/device/`.

## The stock 4.4 kernel (verified)

- **No kexec:** `sys_kexec_load` appears in `/proc/kallsyms` only as a weak stub.
- **`/dev/mem`:** reads all 64 MB of RAM, kernel included. `kptr_restrict` is 0.
- **Memory map:** kernel text and data run from `0x80010000` (`_text`) to `0x808f9b10` (`_end`); the init section from `0x807a2000` is freed after boot. Physical address = virtual − `0x80000000`.
- **Reading stock code:** there's no vmlinux, but a function can be disassembled from RAM: find it in `/proc/kallsyms`, `dd` its pages out of `/dev/mem` on the device, `adb pull`, and run `mipsel-linux-gnu-objdump -D -b binary -m mips:isa32r2 -EL --adjust-vma=<page addr>` in the `r1-stock-modules` image.
- **Watchdog and reboot:** the stock `ingenic_wdt` driver's restart handler arms the watchdog for 160 ticks, so `reboot` is itself a watchdog reset. The X1600 watchdog doesn't use the JZ4740 register layout; `r1jump`'s `arm_watchdog` copies the stock sequence, and `insmod r1jump.ko wdt_only=1 wdt_secs=5` reset the R1 as expected.
- **Module loading:** accepts unsigned out-of-tree modules with no symbol versions. Vermagic is `4.4.94+ preempt mod_unload MIPS32_R2 32BIT `.
- **Building modules:** `kernel/tools/stock-modules/build.sh` builds them from a vanilla kernel.org 4.4.94 tree whose `struct module` matches stock. Check a result with `layout.py` and `imports.py`, run as `uv run --with pyelftools python ...` (the latter needs `/proc/kallsyms` saved to `kernel/out/stock-kallsyms.txt`). The `probe` module loads and unloads on the device.
- **Trap: inline helpers.** Only `struct module` is known to match. Inline helpers that read other kernel structs compile cleanly but misbehave: `alloc_page()` returned NULL on the first call with plenty of free memory. Other examples are `page_to_phys`, `page_address`, `file_inode`, `i_size_read` and `kmalloc`/`kcalloc` (which index the slab caches inline). A module must stick to exported functions (for example `__get_free_pages` and `kernel_read`), and `imports.py` must report nothing missing. `r1jump` follows this and its dry run works.
- **Trap: the OOM killer reboots the R1.** About 15 MB is available while `hiby_player` runs. When a module or `/tmp` (tmpfs, so RAM) takes more, the OOM killer picks `hiby_player` and its launcher reboots the device; this happened with an 8 MB image in `/tmp` plus `r1jump`'s 8 MB copy. Allocate in modules with `__GFP_NORETRY | __GFP_NOWARN`, which in 4.4 fails instead of invoking the OOM killer (verified on the same case).
- **busybox `insmod`** calls a module's init twice when it fails, so its log lines appear twice, and reports a missing file (r1jump's `image=`, after a reset wiped `/tmp`) as "unknown symbol in module, or unknown parameter".

## Mainline status (checked against torvalds master, 7.3 / 7.4 merge window, 2026-10-22)

- **No X1600 platform:** there's no `MACH_X1600`, no X1600 clock (CGU) driver and no `x1600.dtsi`. Ingenic support stops at the X1000 and X1830.
- **Already X1600-aware:** `pinctrl-ingenic` (full X1600 pin data, `ingenic,x1600-pinctrl` and `ingenic,x1600-gpio`, compiled in only with `CONFIG_MACH_X1600`, which upstream doesn't define; our patch 0001 adds it), dwc2 (`ingenic,x1600-otg`). Verified in the 7.3 release; master's `pinctrl-ingenic.c` was identical on 2026-10-22. (A note in between wrongly said 7.3 lacked the pin data: a `grep -rl ... | head` cut the list before reaching it.)
- **Reusable as is (verified 2026-10-23):** OST and MMC through the X1000 compatibles, PDMA through the X1830's (plus a NULL-dereference fix, patch 0014). **Not as is:** I2C and I2S each differ from the X1000 in one register and got `ingenic,x1600-*` entries (patches 0010, 0011). The UART runs through `ingenic,x1000-uart` once UMR is reset (Bluetooth, below) and the TCU through `ingenic,x1000-tcu` (watchdog, below); the X1600's PWM is its own controller (display, below). Untried: SPI (SSI).
- **Board chips covered:** CS43131 (`cs43130` driver), CW2015, BCM43430 Wi-Fi (`brcmfmac`), the touch panel (`hynitron,cst816s`, verified 2026-10-23).
- **Missing:**
  - the Ingenic SFC (the internal NAND flash controller);
  - the X1600 LCD and PWM controllers and the LG35583 panel (our patches 0024–0032 add them; the X1600's LCD controller has nothing in common with `ingenic-drm`'s);
  - Rust-for-Linux (no MIPS support).

## Replacing stock in flash (proposed 2026-10-23, not done)

The user's goal is to drop stock. The design: mainline goes into the `kernel` slot (mtd1) as a compressed uImage, with `uboot`, `kernel2`, `rootfs2` and `ota` left untouched, so Volume Up at power-on with a stock `r1.upt` on the card restores stock through HiBy's recovery ("Boot chain" above). Not `kernel2`: that slot is the recovery. The image must fit 5 MiB, because mainline can't read the internal flash (no SFC driver) and so carries everything it needs before the card mounts. Before writing anything: check that Volume Up starts the recovery on this unit, and cold-boot mainline from RAM over USB boot mode, which shows what it inherits from stock today (clocks, pins, power rails) without touching the flash.

## Plan (approved 2026-10-22)

- **Target:** current mainline, kept as a patch series in `kernel/`.
- **Boot:** the stock SPL and its kernel partition, with the device tree built in.
- **Root filesystem:** an initramfs that mounts the SD card and boots a squashfs image file stored on it. The card isn't repartitioned and no SFC driver is needed at first.
- **Stages:**
  1. SoC base and clocks, to a console;
  2. MMC and USB gadget (ADB);
  3. display, touch and keys;
  4. audio;
  5. AXP2101 and power;
  6. later: NAND, Wi-Fi/BT, USB DAC.
## Mainline on the R1 (2026-10-23)

- **Status:** Linux 7.3 boots through `r1jump` to a busybox initramfs, with its console on the screen, a shell over USB serial and the SD card mounted read-only. Stages 1 (SoC base to a console) and 2 (MMC and USB gadget, as a serial shell rather than ADB) are reached, and since stage 3a the clocks and pins come from real X1600 drivers (patches 0006 and 0007) instead of stand-ins. Stage 3 is done: the display has its own driver (controller, panel and backlight), and touch and all five keys work. Audio (stage 4) plays at 44.1 and 48 kHz, and r1player runs on it (below). Stage 5 is done: the PMIC's rails, power-off, USB power and charger, and the battery gauge.
  - **Verified from a photo of the screen:** system type X1600, `Ingenic XBurst V0.0 FPU V0.0`, BogoMIPS 1099.36 (as under the stock kernel); 56,960 KB total and 49,864 KB free (stock leaves about 1.5 MB free); `simple-framebuffer` registers fb0 and the console runs at 60×50; `/init` starts at 0.28 s and the uptime advances. No errors visible.
- **Building:** `kernel/build.sh` builds in a native arm64 Docker image (an amd64 image under emulation took about 135 s even with nothing to do; native takes about 30 s from scratch and 3 s for a small change). It keeps a 7.3 tree in the `r1-linux` Docker volume (Linux needs a case-sensitive filesystem), applies `kernel/patches/` only when they changed (re-applying them touches `asm/cpu.h`, which nearly everything includes), merges `kernel/r1.config` into `cu1000-neo_defconfig` only when it changed and writes `kernel/out/r1-linux.bin` (vmlinux.bin with the DTB appended, `MIPS_RAW_APPENDED_DTB`). It prints the load address (0x80100000) and entry point. To change the kernel, commit on branch `r1` in the volume tree, then `build.sh patches`. Patch numbers in this document match `kernel/patches` on 2026-10-23 (0001–0040); inserting a patch shifts them. Keep the `DEBUG` boot-marks patch last: a new commit lands after it, so move it before with an interactive rebase (`GIT_SEQUENCE_EDITOR` with a small script; `-i` editors don't work here).
- **ADB under mainline (2026-10-23, `kernel/initramfs/r1-usb`):** the gadget is built through configfs: the serial port (`acm.GS0`, still named "Gadget Serial" for `r1sh.py`) plus ADB through FunctionFS, run by the stock `adbd` that `sdsync.sh` copies to the card. Three traps: `adbd` (buildroot's android-tools 4.2.2) always listens on 127.0.0.1:5037 and exits when it can't, so the kernel needs `CONFIG_INET` and `lo` must be up (`cannot bind 'tcp:5037'`); its `libcrypto` needs `libatomic.so.1`; and the gadget can only be bound once `adbd` has written its descriptors (`ep1` appears). Without `adbd`, or when it isn't up within 3 s, `r1-usb` binds the serial port alone. `INET` costs about 0.6 MB uncompressed once defconfig's NFS, packet sockets and network namespaces are off; the image is 5.06 MB with `xz -9e`, under the 5 MiB `kernel` slot. Measured: `adb push` at 4.7 MB/s, ADB up about 15 s after a reboot through the auto-jump firmware.
- **Booting:** `kernel/tools/boot.sh` pushes `r1-linux.bin` and `r1jump.ko`, pauses r1player, stops the display (below) and jumps. In the new kernel, `kernel/tools/r1sh.py 'cmd' ...` runs commands over the USB serial gadget (it finds the port by its USB name, "Gadget Serial", since an ESP32 also shows up as `/dev/cu.usbmodem*`), and `r1-reboot` (`reboot -f`) there brings the R1 back to r1player in about 6 s. Mainline's watchdog driver takes over the watchdog `r1jump` armed and the kernel feeds it (5 s timeout), so a session lasts as long as the kernel runs, and a kernel that stops scheduling resets within about 5 s. `wdt_secs` now only covers a kernel that dies before the driver probes: the reset then comes after about 0.7 × `wdt_secs`, since `r1jump` counts 32 ticks a second and the watchdog 45.8 (see "Watchdog" below), so `boot.sh 20` brings such a hang back in about 14 s. Mainline's serial shell is up about 3 s after the jump, and `boot.sh` gives up after 20 s. The whole cycle needs no one at the R1: `r1-reboot`, wait for `adb devices` to list it, about 8 s more for the launcher, then `boot.sh`, about 30 s in all. A loop of these caught an intermittent driver failure (1 boot in 4) on 2026-10-23.
- **What the X1600 needed:**
  - **PRId:** the core reports 0x00d00000 (company Ingenic D0, implementation 0), which `cpu_probe_ingenic()` rejects with a silent `panic("Unknown Ingenic Processor ID!")` before any console exists. A patch handles it like the X1830's XBurst1.
  - **OST timer:** same registers as the X1000 (`ingenic,x1000-ost`), but on CPU interrupt 4, not 3. Its only clock input is a fixed 24 MHz `ext`.
  - **Interrupt controller:** the X1000/JZ4780 one at 0x10001000, on CPU interrupt 2.
  - **Display, until its driver probes:** stopped. `boot.sh` stops the controller (CTRL 0x13052000 bit 4, then waits for bit 0 of 0x13052004 to clear) with r1player paused, before the jump, so the screen stays dark from the jump until mainline's display driver starts it (about 1.5 s), and `simple-framebuffer`, the console and the boot-mark stripes draw into memory nothing shows. Left running through the jump it sometimes halted for good (below). Until 2026-10-23 it was left running: the controller rereads a self-linked frame descriptor (register 0x1000) every frame, the stock kernel allocates that descriptor anywhere and replaces it when r1player flips pages, so `boot.sh` chained it to a self-linked copy showing page 0 in the last row of page 1 (0x02776F00), memory of the stock framebuffer that the device tree still reserves. Three ways that went wrong first: assuming a fixed address (the console ended up on the hidden page); a page just past the framebuffer (r1jump allocated it as free memory and overwrote it, and the screen went to garbage); and the boot marks painting both pages (the last stripe overwrote the descriptor, giving vertical lines).
  - **The stock device tree** is readable at `/sys/firmware/fdt`; a decompiled copy is in `kernel/out/stock-dt/` (untracked) and gives every block's address and interrupt.
- **USB (stage 2, 2026-10-23):** the DWC2 at 0x13500000 (`ingenic,x1600-otg`, intc 1) works as a peripheral, with the PHY and clocks as the stock kernel left them. The built-in `g_serial` gadget gives a shell on `/dev/cu.usbmodem*`. `dr_mode = "peripheral"`: host mode needs the USB-C controller as a source and VBUS on PC24 (see "USB-C role" below).
- **SD card (stage 2):** on **MSC1** (0x13460000, intc 36), not MSC0, despite the stock tree's `mmc0` alias pointing at MSC0 (MSC0 is probably the Wi-Fi chip's SDIO link). The X1600's MSC has the X1000's JZ layout, so `jz4740_mmc` (`ingenic,x1000-mmc`) drives it; the stock kernel's many `sdhci_*` symbols are a red herring. It runs in PIO mode (no DMA yet) at about 18 MB/s, and the initramfs mounts the exFAT partition read-only at `/mnt/sd_0`.
- **X1600 clock driver (`x1600-cgu.c`, stage 3a, 2026-10-23):** the register map was read out of the running stock kernel, not guessed. `kernel/tools/stock-modules/clkdump` (a stock-kernel module; only exported functions plus `__clk_lookup` through `kallsyms_lookup_name`) logs every stock clock with its rate, parent, ops symbol and the raw driver structure behind it; `kernel/tools/clkdecode.py` groups them by type. Each mux's parent list came from its `clk_core` (`parent_names` at +20, `num_parents` at +28, verified by the name at +0) read through `/dev/mem`, and the vendor tables `ingenic_mux_table` (identity), `x1600_clk_div_table` (MSC: 2(n+1)) and the PLL descriptors from their kallsyms addresses. The raw dump is `kernel/out/stock-dt/clkdump.txt` (untracked).
  - **PLLs:** rate = ext × M / (N × OD1 × OD0), M bits 31:20, N 19:14, OD1 13:11, OD0 10:8, no offsets (the vendor descriptors say so). The driver keeps them, and the CPU, L2, AHB, APB and DDR clocks, read-only.
  - **Muxes:** register value = parent index. SCLKA {stop, ext, APLL}; CPU/L2, AHB0, AHB2/APB, DDR {stop, SCLKA, MPLL}; peripherals {SCLKA, MPLL, EPLL} (CAN adds ext); I2S {SCLKA, EPLL}.
  - **CDR dividers:** as on the X1830 (change enable 29, busy 28, stop 27), 8 bits wide (4 for PWM and DDR). **Gates:** set-to-disable bits in CLKGR0 (0x20), CLKGR1 (0x28) and OPCR (0x24, bit 23 for the USB PHY). **I2S:** transmit at 0x7c and receive at 0x60, each a mux on bit 30 {SCLKA, EPLL}, an M/N fractional divider (rate = parent × M / N, M bits 28:20, N bits 19:0), an output enable on bit 29 and a gate in CLKGR1 (bit 9 transmit, bit 8 receive). Not in the driver yet: CAN, CDBUS and the memory power gates at 0xf8/0xfc.
  - **Check:** `kernel/tools/clkcompare.py` compares mainline's `clk_summary` with the stock dump: all 50 rates and gate states matched on the first boot.
- **Pins:** the X1600 pin controller (`ingenic,x1600-pinctrl`, 0x10010000, ports A–D every 0x100, GPIO interrupts 17/16/15/14 on intc) claims the SD card's pins (PD0–PD5, `mmc1`). Its GPIO registers (0x10–0x40, 0x70–0x90 per port) read identical under stock and under mainline.
- **Stock clock rates** (from the stock kernel's `/sys/kernel/debug/clk/clk_summary`, saved in `kernel/out/stock-dt/clk_summary.txt`): APLL and CPU 1104 MHz, MPLL 1.4 GHz, EPLL 300 MHz, AHB2 280 MHz (OTG), APB 140 MHz, MSC0 and MSC1 50 MHz (MPLL / 28). The fixed stand-in clocks in `x1600.dtsi` use these. Decoding the PLL registers with the X1830's field layout gives wrong rates (MPLL 1056 MHz).
- **Audio (stage 4, 2026-10-23):** a 440 Hz tone plays cleanly on the headphone output at 44.1 kHz; 44.1 and 48 kHz run at the right rate (measured from the PCM hardware pointer: 44,077 and 48,146 frames/s over 3 s). The chain is all mainline drivers: PDMA (`dma-jz4780` as an X1830, intc 3, AIC request lines 62 TX and 63 RX), the AIC (`jz4740-i2s`, intc 0) as I2S master, the I2S clock from EPLL, and the CS43131 (`cs43130`) on a bit-banged I2C bus (`i2c-gpio`, PB30/PB31, address 0x30, as the stock firmware drives it) behind a `simple-audio-card` with `mclk-fs = 512` (22.5792 / 24.576 MHz, HiBy's MCLKs). PB2 powers the DAC (a fixed regulator) and PB21 resets it. Three driver differences, each a patch:
  - **I2SDIV** holds the bit clock divider itself (not divider − 1 as on the X1000) and keeps only even values: writing 7 stores 6. With the X1000 settings 44.1 kHz played at 58.8 kHz (patch 0010).
  - **`cs43130`** takes the DAI `set_sysclk` frequency as SCLK, but `simple-audio-card` passes MCLK there, so it set up 256-bit slots and played white noise. Patch 0012 adds `set_tdm_slot`, and the R1's DT gives the codec two 32-bit slots (`dai-tdm-slot-num`/`-width`).
  - **`dma-jz4780`** dereferenced a NULL descriptor in `tx_status` after `terminate_all`, which ASoC calls when a stream closes: every close panicked (patch 0014). Master had the same code on 2026-10-22 (734bef548a96). The bug dates from the driver's first commit (d894fc6046fe, 2015) and only shows since `snd_dmaengine_pcm_sync_stop()` calls `dmaengine_tx_status()`, added by 88e98af9f4b5 (v6.11-rc1).
- **Two `cs43130` bugs behind white noise in r1player (2026-10-23), each a patch:**
  - **The clock reference count (patch 0034):** ALSA calls `hw_free()` after any failed `hw_params()`, also when the failure came before the codec's own `hw_params()`, and `cs43130_hw_free()` dropped a clock reference it never took. r1player asks for S32_LE first, which the AIC refuses, then S24_LE: `clk_req` went 0 → −1 → 0, `hw_params()` skipped the switch to the external MCLK, and the DAC ran from its RC oscillator. Every signal then hissed (digital silence stayed silent); r1tone, which opens S16_LE directly, played clean. Check it in `/sys/kernel/debug/regmap/0-0030/registers`: `010006` reads 04 (external MCLK) while a stream plays, 06 (RC oscillator) otherwise. The patch keeps the DAIs holding a reference in a bitmap.
  - **No mute while stopped (patch 0033):** the PCM path stays unmuted until DAPM powers down, `pmdown_time` after close, and a stopped stream hisses at 0 dB. The patch adds `mute_stream`, so ASoC mutes at `hw_free()` and unmutes at `prepare()`. Not on trigger: `mute_unmute_on_trigger` runs in atomic context, and the codec is on I2C. A stream that is open but stopped still hisses, so r1player closes the PCM when paused or stopped.
  - **Formats:** the AIC takes S16_LE and S24_LE (24 bits in a 32-bit container), not S32_LE.
- **96 kHz and up don't work yet:** `mclk-fs = 512` asks the DAC for a 49.152 MHz MCLK, and `cs43130` accepts only 22.5792 and 24.576 MHz. HiBy keeps those two MCLKs for every rate of each family; `simple-audio-card` can't say that.
- **Mono (2026-10-23):** a mono stream gets the same DAC layout as stereo: 64-clock frame, high time 32, channel 2 at bit 32 (CS43131 registers 0x040014 to 0x040019 and 0x050000/0x050001 read over I2C at 0x30 while a silent stream runs). That layout is right on this board: the I2S controller expands mono itself (`AICCR` bit 11, `MONO_TO_STEREO`, 0x...4802 against 0x...4002 in stereo) with the same divider, so two 32-bit slots go out either way. **But mono also needs the AICCR channel field (bits 27:24) written** (patch 0010): left at 1 (two channels, as the stock kernel leaves it), the AIC takes a mono stream two samples per frame, so it plays an octave high and 6 s of mono ends in 3 s, which an earlier "mono is clean in both ears" check missed. Check speed with silence: `r1tone 1000 -200 6 44100 <ch>` takes 6 s in both cases once fixed (2026-10-23, `AICCR` 0x000C4802 in mono; the field being a channel count is inferred from this, no datasheet; listened to on the earbuds the same day: mono and stereo 440 Hz have the same pitch; whether mono is equal in both ears with the fix was not answered). The ASoC core produces that layout by forcing the codec's channel count to the number of `tdm_mask` bits (`soc_pcm_codec_params_fixup()`), which is what two reviewers of the `cs43130` patch object to (below).
- **Volume:** `Master Playback Volume` is attenuation in 0.5 dB steps from −127.5 dB (255 = 0 dB); it boots at 135 (−60 dB). HiBy's driver mutes the DAC around every clock start and stop; mainline mutes it from `hw_free()` to `prepare()` (patch 0033), not around the clock start and stop. Over four mono tone starts and stops on the earbuds (2026-10-23, volume 195, tones at -30 dBFS) there was at most one faint click, once, and the listener was not sure it was real. Not settled: whether mainline pops at stream start or stop; louder levels and other headphones are untested.
- **Touch (2026-10-23):** the panel at 0x15 on I2C1 (PB19/PB20, function 0; intc 60, the stock tree's i2c1; I2C0 is intc 61) works with mainline's `hynitron,cst816s` driver, interrupt PA16 (falling), reset PA17. It reports panel pixels (480 × 800), though the driver advertises 0–240. The X1600 I2C controller differs from the X1000's in one register: the SDA set-up time is at 0xa0 (0x94 is the spike filter), and left at its reset value (116 APB cycles) every transfer ends in a lost arbitration (TXABRT 0x1000). Patch 0011 adds `ingenic,x1600-i2c`. Its power rail is the PMIC's ALDO2, kept always on in the DT since the driver takes no supply.
- **Keys (2026-10-23):** power on PC31 (active low) and next on PC28 (active high) through `gpio-keys`; play/pause, volume down and volume up share ADC channel 0 (0, 1.0 and 1.65 V; 3.3 V released) through `adc-keys`, polled every 50 ms. All five verified, one press each.
- **ADC (patch 0015, a new driver, `ingenic-x1600-adc`):** the SADC at 0x10070000, intc 11, has nothing in common with the JZ47xx ADCs of `ingenic-adc`. ENABLE (0x00) bits 3..0 start a channel and bit 15 powers it down; CTRL (0x08) bits 3..0 mask the channels' interrupts; STATUS (0x0c) is write-1-to-clear; results are 12 bits, channels 0/1 in 0x10 and 2/3 in 0x14 (low and high half); CLKDIV (0x20) holds three dividers (stock: 119, 1, 99 at the 140 MHz APB clock). Reference 3.3 V. Channels: 0 the keys, 1 the headphone jack (stock reads 2.8–3.3 V as plugged; about 3.3 V with earbuds in), 2 the headset remote (2.0 V idle; stock powers it from the PMIC's ALDO4), 3 unused. Jack detection and the remote aren't wired up yet.
- **Display (stage 3, 2026-10-23, patches 0024–0032):** mainline's own driver now runs the screen: `ingenic-x1600-drm` for the controller, `panel-hiby-lg35583` for the panel and `pwm-ingenic-x1600` with `pwm-backlight` for the backlight. Verified: console and RGB565 colours (red, green, blue bands), the panel's power cycle (`echo 4`, then `echo 0`, to `/sys/class/graphics/fb0/blank`) and a brightness sweep (100, 10, 0, 60), by eye; 5 boots of three screen off/on cycles each, after the last fix, without a timeout.
  - **Controller (0x13050000, intc 31):** FRM_DESC (0x1000) takes the address of a frame descriptor (next, frame address, stride in pixels, format in bits 22:19 of word 3: 2 RGB565, 4 32-bit; bit 17 of word 4 as the vendor sets it) and FRM_START (0x1004) starts the fetch. The driver keeps two self-linked descriptors and flips by writing the other's address to FRM_DESC and setting FRM_START, as the vendor driver does; the controller takes it at the end of the frame. Flipping by relinking the shown descriptor instead completed a frame late: r1player drew into a page still on screen, and scrolling tore at mid-screen (seen 2026-10-23). CTRL (0x2000) bit 4 stops at the end of the frame; ST (0x2010) bits 7 stopped, 8 underrun, 17 descriptor fetched, CLR_ST (0x2008) and INT_EN (0x200c); COM_CFG (0x8000) the interface (1 TFT) and dithering; TFT timings at 0x9000–0x900c (sync length or start in bits 27:16, total or end in 11:0) and TFT_CFG (0x9010: polarities in bits 10:7, colour order 2 in 21:19 and 18:16, as stock). The stock timings, read back from the registers: 552×827 total, 24/24/24 horizontal and 8/14/5 vertical (back porch, front porch, sync), 28 MHz from MPLL ÷ 50 (61 Hz).
  - **Two traps, each found by a failure:** a status bit is only set while its interrupt is enabled, so polling for "stopped" with INT_EN cleared never succeeds; the first driver's stop at probe always timed out, and when the stop landed after the first start (1 boot in 4) the controller stayed stopped and every vblank wait timed out. And a status bit set just before its interrupt is masked keeps the line raised: a handler that only cleared enabled bits returned IRQ_NONE until the kernel disabled IRQ 31 ("nobody cared", about 5 s after boot, when vblank turns off). The driver now waits for the stop through the interrupt, clears every pending bit in the handler, and clears a bit when it masks it.
  - **Pins:** the panel takes 18 bits on the six most significant lines of each colour of the 24-bit bus (PA2–PA7, PA10–PA15, PA18–PA23, plus PA24–PA27 for clock, DE and syncs), leaving PA0/PA1 to the panel's SPI and PA16/PA17 to the touch panel. No mainline group matched, so patch 0024 adds `lcd-18bit-msb`.
  - **Panel:** R1s ship with an LG35583 or an ST7701S; ADC channel 3 tells them apart (below 1000 mV: LG35583). This unit reads 0 mV. Both are set up over a bit-banged 3-wire SPI (SCK PA0, MOSI PA1, CS PA30, reset PA31, active low), here `spi-gpio`. The LG35583 takes 16-bit words: `0x20` and a register's high byte, `0x00` and its low byte, `0x40` and a data byte (`hiby,lg35583`, sequence from the vendor driver; its controller is unidentified). The ST7701S variant would need an entry in mainline's `panel-sitronix-st7701` and a way to pick the panel at boot; neither exists.
  - **Backlight:** PC0 is channel 0 of the X1600's own PWM controller (0x134c0000), not a TCU channel (`pwm-jz4740`). Per channel: a divider of 2^n (CCFG, 0x40 + 4n) and a waveform word (WCFG, 0x80 + 4n: counts at the period's starting level in bits 31:16, at the other level in 15:0), loaded by UPT (0x10) at the end of the period (BUSY, 0x14); ENS/ENC (0x00/0x04) switch channels on and off, EN (0x08) reads them back; INL (0x24) and IDL (0x28) hold the starting and idle levels. A word needs one count of each level, so 0 and 100% switch the channel off with the idle level set. Clock: EPLL, 300 MHz. Stock runs it at 30 kHz; channels 1 and 2 (PC1, PC2) are the red and blue LEDs, not described yet.
  - **The controller halts after an underrun (fixed in `boot.sh`, 2026-10-23):** left scanning out stock's frame through the jump, it was found halted at probe on about 1 boot in 13 (6 of 79; 8 of 100 in the measurement below): register 0x2004 (undocumented, a live state: 0x0f running, 0x06 or 0x20006 stopped) reads 0x10f, no descriptor is fetched (IRQ 31 counts 0, vblank waits time out) and it ignores the end-of-frame stop, the quick stop (CTRL bit 1) and FRM_START until a reset. Bit 8 is the underrun bit of ST, which stock enables; the likely cause is the memory traffic of `r1jump`'s copy and the new kernel's start-up starving the scan-out (not proven). A measurement over 100 boots, with the probe's stop written at a random point of the frame and its phase logged, found the 8 halted controllers already halted before the stop (no frame started in the 40 ms before it): the stop does not cause it, and timing it (an earlier attempt, written 5 ms after a frame start) did not help, 2 halted in 40. Stopping the controller on the stock side before the jump: 100 boots of 100 good (2026-10-23), the state a cold boot from the SPL would also leave. The driver logs "The controller is halted after an underrun" if it finds one.
  - **Not done yet:** 32-bit (XRGB8888) frames, untested; the emulated fbdev's memory is coherent DMA memory, uncached on MIPS (r1player scrolls smoothly on it, by eye); the 1.5 MB of stock pages stay reserved after the handover; `clk_ignore_unused` is still in `bootargs`.

Nothing is written to the card, and a reboot undoes it. Push each new build under a new name: pushing onto the one running fails (text file busy), and `umount` of the busy bind fails too, but a second `mount --bind` stacks on top and takes effect. - **Bluetooth (2026-10-23, after the watchdog patches: the serial binding, the X1600's UARTs, the R1's Bluetooth node and `serial: 8250_ingenic: start the X1000 UART from 16 clocks a bit`; `kernel/initramfs/r1-bt`):** pairing, connecting and A2DP playback to a headset work under mainline (an OpenRun Pro 2, SBC at 48 kHz: a 440 Hz tone through `bluealsa-cli open`, twice in a row, heard). r1player's side (its Bluetooth page: `bluetoothctl` on a pseudo-terminal, which needs `/dev/pts`, and output through `bluealsa-cli open`) and pairings that survive a restart were verified on 2026-10-23 with the same headset: it reconnected by itself after a restart, its PCM present about 30 s after boot. HiBy built `bluetoothd` with its storage in `/usr/data/bluetooth` (not `/var/lib/bluetooth`: `strings bluetoothd`), in RAM under mainline; r1player saves it after a pairing as `$R1_STATE/bluetooth.tar` on the card (a tar, because exFAT refuses the colons in BlueZ's directory names: "Invalid argument"), and init unpacks it at boot. Pairings are not shared with stock (the goal is to drop stock).
  - **The chip:** the AP6212 module's BCM43430A1 (chip id 94) on UART0, PB7/PB8 data and PB9/PB10 RTS/CTS (function 0, mainline's `uart0-data` and `uart0-hwflow`). BT_REG_ON is PB4 and the host's wake line to it PB5, both active high (the stock kernel's GPIO labels `bt_reg_on`, `host_wake_bt`; no line from the chip back to the SoC is labelled). Wi-Fi's WL_REG_ON is PB3. Its 32 kHz clock leaves on PC26 (function 0, label `clk32k_out_o`), which the stock kernel sets up and mainline doesn't touch: a cold boot from the SPL will need a pin group and whatever enables that output.
  - **Line speed:** stock runs the link at 3 Mbaud with UMR (0x24, clocks a bit) at 8 and a divisor of 1 on the 24 MHz crystal. `8250_ingenic` never programmed UMR, so it inherited the 8 and every rate came out doubled: hci_bcm's first vendor command failed with `command 0xfc18 tx timeout` and `failed to write update baudrate (-145)`. The patch resets UMR to 16 and UACR to 0 at probe; the link then runs at `max-speed` 1.5 Mbaud, the most 24 MHz / 16 allows. Enough for SBC and aptX; LDAC would want 3 Mbaud, which needs UMR support in the driver.
  - **Firmware:** stock's `bt_init` picks it by the module's SDIO chip vendor (`/sys/devices/platform/md_ingenic,mmc.0/.../chipvendor`, 0x81 aw-nb372sm, otherwise AP6212): this unit takes `BCM4343A1_001.002.009.1010.1030.hcd`, which `sdsync.sh` copies on the R1 to the card as `brcm/BCM43430A1.hcd` (btbcm's name; `/lib` is on the card). hci_bcm first sets the chip up before the card is mounted ("Patch file not found"), so `r1-bt` unbinds and binds `serial0-0` from `hci_uart_bcm` after the mount; the chip then reports `BCM43438A1 26MHz AP6212A1_CL1 BT5.2 OTP-BD[Version: 1010.1030]`.

- **Watchdog (TCU at 0x10002000; tested 2026-10-23 by arming it by hand with `devmem` on a mainline boot):**
  - **Reset compare:** the low half of TDR (0x00). With 320 ticks there the R1 reset after about 10 s; with 320 in the high half and 0xffff in the low half it was still up after 46 s. `r1jump` also writes 2/3 of the timeout into the high half, as the stock driver does; what that half does is unknown.
  - **Clock:** EXCLK / 512 = 46875 Hz, divided by 1024 = 45.8 ticks a second, when TCSR selects the "RTC" input. OPCR (0x10000024) bit 2 picks that source; it reads 0 under both kernels, and the stock clock tree calls the mux `mux_wdt` with parent `ext_div_512`. The RTC module itself runs from the 32768 Hz crystal (`gate_rtc`).
  - **Feeding:** setting TCSR (0x0c) bit 10 zeroes the counter, as the stock driver's ping does. Writing 0 to TCNT (0x08), as mainline's `jz4740_wdt` pings, doesn't: armed for 640 ticks, the R1 reset after about 16 s.
  - **Mainline driver (patches 0035–0039; verified 2026-10-23):** `jz4740_wdt` with a TCSR-bit-10 ping for `ingenic,x1600-watchdog`, and it keeps a watchdog it finds running (`WDOG_HW_RUNNING`), so the kernel feeds it until userspace opens `/dev/watchdog0`. The CGU's "rtc" is a mux on OPCR bit 2 between `ext/512` and `osc32k`. After boot `clk_summary` shows `ext/512` → `rtc` 46875 Hz → `wdt` 45 Hz, and TDR reads 0xE1 (5 s). Booted with `r1jump` armed for 20 s, the R1 was still up at 30 s. The TCU node also brings in `ingenic-timer`, whose clocksource (on "ext") loses to the OST.
  - **Trap, the CGU's parent order:** the Ingenic CGU core registers clocks in ID order and finds a clock's parents among those already registered. A parent with a higher ID than its child gives the clock core NULL parent names, and the kernel hung before its console. Parents need lower IDs, as on the JZ4770: OSC32K is 1, and EXT512 and RTCLK come last.
  - **Trap, the TCU clocks' reset:** registering the TCU clocks reset each channel's TCSR to divider 1, the watchdog's included (patch 0036 skips it when TCER is set). Without that, the watchdog `r1jump` armed for 120 s counted 1024 times faster and reset the R1 about 3 s after the jump, with nothing on screen to show it.

This is how the PRId panic was found.
- **Kernel log after the reset:** mostly lost. `__log_buf` (phys 0x976134) lies past the stock kernel's image, but the stock system reuses that memory before ADB comes up.

- **Jumping to our own code works (2026-10-23).** `r1jump` loaded `kernel/tools/fbpaint` (176 bytes at `0x80010000`), which painted colour bands over the whole screen; the watchdog brought the R1 back about 15 s later.
  - **Why the first attempt failed:** the stub, its params and the page list were written through cached KSEG0 but executed and read through uncached KSEG1, so the CPU ran stale RAM (254 of the stub's 276 bytes hadn't reached it). `r1jump` now writes them back from L1 and L2 first, and a dry run prints `uncached view differs: stub 0, params 0, list 0 bytes` to show it.
  - **The screen is a debug channel:** the LCD controller refreshes continuously at 60 Hz (the `jzfb` interrupt), straight from the framebuffer at physical `0x02600000` (480×800 RGB565, 960-byte lines, two pages). A new kernel can paint progress there with uncached stores and no display driver, as long as it leaves the LCD controller and its clocks alone. Writes from Linux through `/dev/mem` show up too.
- **Debugging without serial (superseded):** the user has no serial adapter. What works instead: the boot-mark stripes and the framebuffer console on screen, then the USB serial shell once the kernel is up. Recovering a crashed kernel's log from RAM after the reset does not: DRAM keeps its contents through a watchdog reset and the SPL, but the stock boot reuses free memory before ADB is up. `kernel/tools/ramtest.sh` measured it on 2026-10-22: 2 of 1044 marker pages left when checked 4 minutes after boot, 0 of 1040 when checked as soon as ADB came back (7 s).

**Replies so far (2026-10-23):**
- **`cs43130` RFC:** the review bot (`sashiko-bot@kernel.org`) and then Charles Keepax of Cirrus. Both want the masks checked (`== 0x3`) and, if the callback stays, full TDM support: save the slot numbers and use them in `cs43130_set_sp_fmt()` instead of `params_channels()`. Keepax would rather the card did not call `set_sysclk` at all (no `mclk-fs`), then the codec's own code would do. Our reading, not tried: the R1 needs `mclk-fs`, because in `simple_util_hw_params()` the host clock rate is only set inside `if (mclk_fs)` and the I2S driver does not set it; and a clock-slave codec like ours returns "SCLK freq is not set" from `cs43130_hw_params()` when `set_sysclk` gave it no SCLK, so dropping the calls would fail the stream unless something else supplies the bit-clock rate. A v2 is not written.

The code does what the bot says (checked in the source); whether the R1 reaches it is unconfirmed, since the replug test had an active bus. Untested: unplug while the host has suspended the bus.
