# Mainline Linux for the HiBy R1

- `kernel/`: the mainline port. The patch series lives in `patches/`. `build.sh` builds it in Docker; to change the kernel, commit in the volume tree on branch `r1`, then run `build.sh patches`. `initramfs/` holds init and its scripts. `tools/` has the flash, card and system installers, `r1sh.py` (the USB serial shell), `usbboot/`, and the tools for the stock kernel.
- `firmware/`: builds a patched HiBy update (ADB, and the launcher that jumps to mainline) from the unpacked stock 1.6 update in `stock/`. `overlay/` holds the files the image adds; `patches/` holds the changes to HiBy's own files. `build.sh` applies both and writes `out/r1player/r1.upt` through `repack.sh` and `verify.sh`. Edit `overlay/` or `patches/`, never `patched/`, which `build.sh` recreates. `verify.sh` exits 1 whenever the image differs from stock, which is always for a patched image: read its `ok`/`FAIL` lines instead.
- `docs/kernel.md`: the boot chain, what the stock kernel allows, the port's status, measurements and upstream submissions. Read it before any kernel or boot loader work.
- `docs/r1-device.md`: hardware facts and how ADB access works. Read it before touching firmware, audio routing or input.

## Rules

- Never commit HiBy's files: the stock update, anything unpacked or built from it (`firmware/stock`, `patched`, `out`, `kernel/out/system.squashfs`), or a whole copy of one of their scripts. Changes to their files go in `firmware/patches/` as diffs.
- adb only sees the R1 when its server was started with `ADB_LIBUSB=0`; if adb was already running, run `adb kill-server` first.
- On mainline, the stock SPL boots the kernel in the `kernel` flash slot. Its `r1-loader` kexecs the SD card's `/.r1-mainline/r1-linux.bin`, whose init runs `/.r1-mainline/app` (else `r1player`, its earlier name) from a copy in RAM. Kill `/tmp/app` (or `/tmp/r1player`) and the next start takes the card's build. ADB lists the R1 as `r1-mainline` (root shell). There is no stock system and `/usr/data` is in RAM, so `kernel/tools/sdsync.sh` (run from stock) doesn't apply.
- Deploy an app or a kernel with `adb push` to `/mnt/sd_0/.r1-mainline/`, between `mount -o remount,rw /mnt/sd_0` and `mount -o remount,ro /mnt/sd_0`. A kernel also needs its `entry` file (`docs/kernel.md`). First check the card is mounted (`grep ' /mnt/sd_0 ' /proc/mounts`): while it's shared with a computer as a USB disk (`/tmp/sd-shared`), a push lands in RAM and fills it.
- Over ADB, avoid anything that cuts USB or needs much RAM: with an app and Bluetooth up, about 21 MB is free, and `r1kexec` from a running system gets OOM-killed.
- A card kernel that doesn't come up makes every later start stay on the flash kernel, until `r1-linux.bin` changes or `/.r1-mainline/kexec-pending` is removed. Volume Down held at power-on also stays there. The last boot's log is in `/sys/fs/pstore`. Volume Up held at power-on, with an `r1.upt` at the card root, reflashes that update through HiBy's recovery.
- `mksystem.py` and `sdsync.sh` take the app's build from `R1_APP`.
- For now the flash kernel is minimal (`kernel/r1.config`) and Wi-Fi is only in the card kernel (`kernel/r1-card.config`). With the Wi-Fi nodes or `CONFIG_MODULES` in the flash kernel, some starts lost USB until a power-off, cause not found (`docs/kernel.md`, "USB lost at some starts"). The goal is a complete flash kernel: test any addition to it with restart loops.
